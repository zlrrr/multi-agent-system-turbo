# 项目宪章 — multi-agent-system-turbo（MAS-Turbo）

> **状态**：已批准 · **版本**：1.0.0 · **批准日期**：2026-08-23 · **最近修订**：2026-08-23
> **双语对应文件**：[`constitution.md`](./constitution.md) —— 两份文件**必须在同一次提交中**同步修改。

宪章是本仓库中优先级最高的文档。所有规格说明、计划、设计文档、任务清单、代码以及发布制品
都从属于本文档。当任何其他文档与本文档冲突时，**以本文档为准**，冲突的另一方即为缺陷，必须
被修正。

---

## 第一条 — 规格驱动开发（SDD）是强制性的

**I.1 无规格，不写码。** 任何行为性变更都必须可以追溯到 `specs/NNN-slug/` 下的一个编号特性。
链路是固定的，每一环都是可评审的产出物：

```
项目目标 (docs/*/project-goals.md)
  └─> spec.md         做什么 & 为什么（不含技术选型）
        └─> plan.md   怎么做（技术栈、约束、风险）
              └─> design-hld.md   系统分解、接口、数据流
                    └─> design-lld.md   包 / 类型 / 函数级契约
                          └─> tasks.md  可执行、有序、可测试的工作单元
                                └─> 代码 + 测试
                                      └─> 制品（镜像、二进制、文档）
```

**I.2 上游优先。** 变更必须在其所属的最高层次发起，然后**逐层向下级联**。为了修复某个与规格
相矛盾的行为而直接改代码，属于违宪行为；正确做法是先改规格，再级联，最后改代码。

**I.3 可追溯性由机器校验。** 每条需求都有稳定 ID（`FR-###`、`NFR-###`、`CON-###`）。每个任务
都必须声明其满足的需求 ID。每个导出包都必须标注管辖它的设计章节。当某条需求没有对应任务，或
某个任务引用了不存在的需求时，`make sdd-verify` 必须让构建失败。

## 第二条 — 级联修订

**II.1 修订必须显式记录。** 对上游产出物的任何变更，都必须在该产出物的 `## Change Log` 表格中
记录，包含版本号提升，以及一列 *Impact*，指明哪些下游产出物需要重新推导。

**II.2 级联被跟踪，而非被假定。** `specs/NNN-slug/traceability.yaml` 记录每个产出物的版本。
当上游版本提升时，下游条目变为 `stale` 状态，`make sdd-verify` 将持续失败，直到每个条目被
重新评审并重新盖章。

**II.3 目标允许修正。** 当现实与项目目标文档不一致时，目标文档本身也可以在同样的级联纪律下被
修订。目标漂移必须被**记录**，绝不允许静默发生。

## 第三条 — 双语文档对等

**III.1** `docs/`、`specs/`、`.specify/` 下的每一份文档都同时存在英文版（`X.md`）与简体中文版
（`X.zh.md`）。

**III.2** 两份文件**在同一次提交中**更新。只改其中一份的提交会被 `make sdd-verify` 拒绝。

**III.3** 两份文件语义对等。任何一份都不是另一份的摘要。标识符、需求 ID、错误码、类型名、
命令行参数**不做翻译**。

## 第四条 — 安全：永远只读

**IV.1 系统不对任何目标环境执行任何变更类操作。** 不写入、不删除、不重启、不扩缩容、不改配置、
不执行任何会改变状态的 `exec`。这不是一个默认值，而是一条由代码强制保证的不变量——每一次工具
调用都必须经过安全守卫。

**IV.2 默认拒绝。** 未被显式加入白名单的命令、HTTP 方法或 API 路径一律拒绝。新增能力 = 新增
白名单条目 = 一次规格变更。

**IV.3 只给建议。** 系统的输出是分析结论加上给人类的**建议**动作。它绝不表现得好像自己已经
执行过某个操作。

**IV.4 密钥绝不外泄。** 凭据必须从日志、追踪、报告以及发送给任何 LLM 供应商的提示词中脱敏。

## 第五条 — 工具自身的可观测性

**V.1 结构化日志。** 所有日志均为结构化（`slog`），携带 `run_id`，端到端可关联。

**V.2 每个错误都带错误码。** 暴露给用户或日志的错误必须携带来自中央注册表的稳定 `MAS-NNNN`
错误码，并附带双语描述与修复建议。到达边界层仍未携带错误码的错误即为缺陷。

**V.3 运行可重放。** 每次诊断运行都持久化其证据、提示词、工具调用与结论，使得结果无需重跑即可
审计。

## 第六条 — 测试先行的检查点

**VI.1** `tasks.md` 中的每个任务都必须在实现**之前**声明其验收测试。

**VI.2** 只有当任务的测试在 CI 中通过时，该任务才算 `done`。不存在部分完成。

**VI.3** 确定性：LLM 行为通过脚本化的 mock provider 测试。任何测试都不得依赖网络或真实模型。

## 第七条 — 架构品味

**VII.1 抽象必须自证其价值。** 一个接口之所以存在，是因为它（现在或可预见地）有至少两个实现，
或者因为它是测试所需的接缝。

**VII.2 在领域会变化的地方做可插拔，其余地方做具体实现。** LLM 供应商、Agent 拓扑、遥测数据源、
环境适配器、中间件知识包是会变化的——它们以注册表方式插件化。其余部分不做插件化。

**VII.3 确定性优先。** 如果一个问题可以由规则回答，就让规则回答它。LLM 推理留给真正需要判断力
的部分。

**VII.4 内核依赖极简。** `internal/core` 只依赖标准库与本仓库自身。

## 第八条 — 交付

**VIII.1** 交付物是容器镜像加带版本号的二进制，由 GitHub Actions 从打了标签的提交产出，并附带
双语用户手册。

**VIII.2** `main` 分支始终可发布：`make ci`（lint、vet、单元测试、集成测试、构建）保持绿色。

## 第九条 — 自主（“黑灯”）运行

**IX.1** 只要优先级列表中还有未被阻塞的条目，开发就在无人干预的情况下持续推进。

**IX.2** 仅在以下情况请求人工介入：不可逆或对外的操作、凭据、目标层面的真实歧义（不同解读会
导致产出实质不同的系统）、或外部阻塞。

**IX.3** 为了保持推进而做出的任何假设，都必须记录在受影响产出物的 `## Assumptions` 章节中，
以便人类事后审计与推翻。

---

## 修订流程

1. 在同一次提交中同时修订 `constitution.md` 与 `constitution.zh.md`。
2. 提升版本号：MAJOR = 删除/重定义某一条，MINOR = 新增某一条，PATCH = 措辞调整。
3. 在下方记录本次修订。
4. 运行 `make sdd-verify`；解决它标记为 `stale` 的每一个产出物。
