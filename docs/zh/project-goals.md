## 1. 使命

构建一个 **由 LLM 驱动的多 Agent 系统，用于诊断开源中间件的运行时问题** —— Redis、MongoDB、
Pulsar、Kafka、OceanBase、Milvus 等 —— 通过关联指标、日志、集群实时状态与上游源码，输出
有证据支撑的分析结论，并为人类运维人员给出**建议性**处置措施。

系统**绝不变更目标环境**。它只读取、推理、给建议。

## 2. 为什么这件事难（以及为什么 Agent 系统是正确的形态）

中间件故障定位本质上是**在时间压力下、在异构证据集合上做搜索**。解释一次故障的关键信号，可能
藏在某条 PromQL 曲线里、藏在 40 分钟前的一行日志里、藏在一条 Kubernetes 事件里、藏在
`redis-cli INFO` 的某个字段里，也可能藏在实际部署版本对应的某个上游已知缺陷里。资深 SRE 通过
不断提出并淘汰假设来收敛这个搜索。这个循环 —— 提出假设 → 定向采集证据 → 证伪或证实 → 升级或
下结论 —— 恰恰是一个结构良好的 Agent 系统能够承载的，前提是：

- 证据采集必须**廉价、安全、有边界**（只读、白名单、限流）；
- 领域知识必须**显式化并有版本**，而不是塞进提示词里；
- 确定性检查必须在任何模型被要求思考**之前**先跑（宪章 VII.3）；
- 每一条结论都必须**可追溯到产生它的证据**。

## 3. 目标分解

使命陈述被穷尽地分解为若干目标域。每个目标域拥有一个 ID，供下游规格说明引用。

### G1 — 诊断内核
| ID | 目标 | 成功信号 |
|---|---|---|
| G1.1 | 接受一个诊断请求：指定目标中间件实例、症状、时间窗口 | 请求被校验并受理，或以带错误码的方式被拒绝 |
| G1.2 | 输出带置信度与支撑证据的、经过排序的假设集合 | 报告至少含 1 条假设，每条至少引用 1 项证据 |
| G1.3 | 输出**仅供参考**的处置建议 | 每一步都标注风险等级，且必须由人类执行 |
| G1.4 | 每次运行事后可复现、可审计 | 运行记录可重放证据、提示词、工具调用与结论 |
| G1.5 | 数据源缺失时优雅降级 | 报告明确说明哪些源不可用，以及这对结论意味着什么 |

### G2 — 中间件覆盖
| ID | 目标 | 成功信号 |
|---|---|---|
| G2.1 | 中间件专属知识以**数据包**形式存在，而非代码 | 新增中间件无需重新编译 |
| G2.2 | 提供 Redis、Kafka、MongoDB、Pulsar、Milvus、OceanBase 知识包 | 每个包声明信号、日志模式、失效模式、排查剧本 |
| G2.3 | 知识包具备版本感知能力 | 包内规则可限定适用版本区间 |
| G2.4 | 第三方可编写知识包 | 知识包 Schema 公开并可校验 |

### G3 — 遥测数据接入
| ID | 目标 | 成功信号 |
|---|---|---|
| G3.1 | 查询 Prometheus 兼容指标（Prometheus、VictoriaMetrics、Thanos、Mimir） | 支持带鉴权的瞬时与区间查询 |
| G3.2 | 查询 Loki 兼容日志 | 支持 LogQL 查询、标签发现、结果集限额 |
| G3.3 | 端点、鉴权与标签映射均由**用户配置** | 代码中不存在任何硬编码端点 |
| G3.4 | 遥测数据源在同一接口后可插拔 | 新增数据源 = 新增一条注册表项 |

### G4 — 运行模式
| ID | 目标 | 成功信号 |
|---|---|---|
| G4.1 | **离线模式**：仅基于遥测/日志快照进行分析 | 在无法访问实时集群时仍可运行 |
| G4.2 | **在线模式**：在实时环境中执行只读巡检命令 | 命令要么通过安全守卫，要么被拒绝 |
| G4.3 | 模式可按运行、按目标分别选择 | 配置与请求都可对其施加约束 |

### G5 — 环境适配器
| ID | 目标 | 成功信号 |
|---|---|---|
| G5.1 | Kubernetes 适配器（主）：Pod、事件、日志、节点、容器内只读 exec | 集群内与 kubeconfig 两种方式均可用 |
| G5.2 | 本地/二进制适配器：进程、端口、资源占用、配置与日志文件 | 适用于中间件运行在 K8s 之外的场景 |
| G5.3 | 适配器共享同一接口，使 Agent 与环境无关 | 同一份 Agent 代码可驱动两种环境 |

### G6 — 源码获取
| ID | 目标 | 成功信号 |
|---|---|---|
| G6.1 | 从**网络**仓库获取中间件源码 | 可按 ref 克隆/拉取 |
| G6.2 | 从**本地**仓库或镜像获取 | 完全离网环境下可用 |
| G6.3 | **网络不通时自动回退到本地** | 网络故障导致的是回退，而不是运行失败 |
| G6.4 | 在源码中检索符号、错误字符串与日志格式 | 可以把观察到的日志行定位到源码位置 |

### G7 — 多 Agent 架构
| ID | 目标 | 成功信号 |
|---|---|---|
| G7.1 | 角色划分遵循业界主流实践：规划、专项调查、关联分析、批判、报告 | 角色显式存在且可独立测试 |

## 5. 优先级 backlog（业界实践：走通骨架 → 做深 → 做宽）

一致采用的优先级规则：
**优先级 =（消解的风险 × 用户价值）÷ 成本**，并附加一条硬约束：必须先建成**走通的骨架**
（一条贯穿所有架构层次的最细端到端路径），然后才允许把任何一层做深。正是这一点，让第一个
里程碑产出的是真正可用的东西，而不是一堆互不相连的零件。
