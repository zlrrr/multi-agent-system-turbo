# 概要设计（HLD）：给目标与凭据加上租户维度

> **特性 ID**：`011-tenant-registry` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它位于何处

```
  配置 ──► targets[].tenant ───────────┐
           auth.tokens[].tenants ────┐ │
                                     ▼ ▼
  请求 ──► 授权（009） ──► Principal{Name, Scopes, Tenants}
                                     │
                                     ▼
                              mayReach(target)  ── 一个函数，覆盖每条路径
                                     │
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
      POST /diagnoses          GET /targets           GET /diagnoses[/id]
      不可达时返回 404          过滤后的列表           过滤后的列表
```

请求路径上没有新增任何东西：租户集合搭在特性 009 已经解析出的主体上，
并由一个函数回答唯一的那个问题。这是刻意的 ——
第二个收口点就是第二件要记住的事，而这个特性之后写下的第一个处理函数就会忘掉它。

## 2. 租户是自己开启的

用一个开关来启用它是最显而易见的做法，而它有两种失败模式、没有任何好处。
"配了租户却关着"，是一个看起来已分区、实际并没有的部署。
"开着却没有租户"，则是一个以"没人能解释的空列表"形式浮现的配置错误。

所以这里没有开关。**只要有任何一个目标写下了 tenant，这份配置就是多租户的**，
随之而来的规则在加载时生效：

| 配置情况 | 结果 |
|---|---|
| 没有任何目标写 tenant | 租户关闭；与今天完全相同，也没有任何新东西要配 |
| 一部分目标写了，另一部分没写 | 拒绝。不属于任何人的目标，要么谁都能碰、要么谁都不能碰，而这两个答案都只是猜测 |
| 所有目标都写了，但某个凭据没写 | 拒绝。已分区部署里不受限的凭据，是一个没有人声明过的超级用户 |
| 所有目标与所有凭据都写了 | 租户开启 |

这与特性 009 处理监听地址的形态相同，理由也相同：
要求由"配置说了什么"推出，而不是由一次单独的意图声明推出，
因此它不可能同时"成立"又"未被强制执行"。

而单团队部署 —— 也就是其中的绝大多数 —— 永远不会遇到这一切。

## 3. 一种不回答问题的拒绝

用"你无权访问 `payments-redis`"来拒绝一个跨租户目标，
等于确认了 `payments-redis` 的存在。
而这恰恰是另一个租户指望不被泄露的那个事实，
并且攻击者每猜一个 id，它就泄露一次。

因此，从调用者所处的位置看，另一个租户的目标**并不存在**：
与一个从未被配置过的 id 拥有相同的状态码、相同的错误码、相同的响应体。
这个区别在进程内部是真实的，在外部则不可见 ——
而那是它唯一能安全存在的地方。

对运行记录同理。属于另一个租户的运行 id 是"未找到"，而不是"被禁止"。

## 4. 运行上的租户

运行记录已经写明了是谁请求的。从此它还会写明**这次是给哪个租户做的**，
且是在准入阶段记录，而不是事后推导。

事后推导意味着在读取时去查目标的租户，而那回答的是另一个问题：
*那个目标现在属于哪个租户*。配置会变；而审计问的是过去。
在事情发生时就把它写下来，是唯一始终为真的版本。

## 5. 刻意不做的事

- **不做其他任何按租户的配置。** 模型、预算、知识包与遥测数据源仍是全局的。
  它们每一项都是合理的诉求，也都有各自的答案；
  而一个会悄悄换掉模型的租户，是没有人要求过的意外。
- **不做层级、分组或委派。** 一组扁平的名字。
  第一版就带层级的租户模型，是没有人能推理清楚的；
  而且与"缺失的特性"不同，它以后拿不掉。
- **不做按租户切分的存储布局。** 运行记录仍存放在同一处，只是带上租户标记。
  切分桶是保留策略的决定，把它与访问控制的决定混在一起，会让两者都更难改。
- **不给 CLI 加租户。** 它以运维人员的身份、用运维人员自己的配置文件运行。
  那个文件里的每个目标本来就是他们的，而在自己的文件里划一条分界线，保护不了任何人。
