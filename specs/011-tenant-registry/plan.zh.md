# 实施计划：给目标与凭据加上租户维度

> **特性 ID**：`011-tenant-registry` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 思路

机制不过是目标上的一个字符串、凭据上的一个列表。
真正必须做对的是：这套机制什么时候开启，以及在哪里强制执行。

**什么时候开启。** 用一个开关是最显而易见的答案，也是错的那个：
配了租户却没开开关的部署，是在静默地毫无防护；
开了开关却没有租户的部署，是一个没有人会发现的配置错误。
因此，租户是自己开启的：**只要有任何一个目标写下了 tenant，
这份配置就是多租户配置**，随之而来的规则在加载时强制执行 ——
每个目标都必须写，每个凭据都必须说明它能代表哪些租户。
没有什么要记，也没有什么会忘；而单团队部署永远不会知道这套东西存在。

这与特性 009 处理 API 监听地址的形态相同：
要求由"配置实际说了什么"推出，而不是由一次单独的意图声明推出。

**在哪里强制执行。** 与凭据在同一个地方，理由也相同：
会自行过滤的处理函数，总有一天会被复制走，而过滤不会跟着一起走。
授权器本就为每个请求解析出主体；租户集合搭在它上面，
由一个函数回答"这个主体能不能看到这个目标"。

**拒绝时该说什么。** 用"你无权访问目标 `payments-redis`"来拒绝，
等于确认了 `payments-redis` 的存在 —— 而这恰恰是另一个租户不想告诉你的一半信息。
跨租户的目标被当作**不存在**处理 —— 从调用者所处的位置看，它本来就是不存在的。

## 2. 设计决策

| ID | 决策 | 理由 |
|---|---|---|
| D-1 | 只要有目标写了 tenant，租户即开启 | 开关可能"配了租户却关着"，那是静默暴露；也可能"开着却没有租户"，那是没人会发现的坏配置 |
| D-2 | 一旦开启，每个目标都必须写 tenant | 多租户部署里一个不属于任何人的目标，要么谁都能碰、要么谁都不能碰，而这两个答案都只是猜测 |
| D-3 | 一旦开启，每个凭据都必须写 tenants | 多租户部署里一个不受限的凭据，是一个没有人声明过的超级用户 |
| D-4 | 跨租户目标返回 404 而不是 403 | 403 会确认该目标存在 —— 那是邻居的信息，不是调用者的 |
| D-5 | 一个扁平命名空间：不做层级，不做分组 | 第一版就带层级的租户模型，是没有人能推理清楚的，而且以后拿不掉 |
| D-6 | 租户只作用于 API，绝不作用于 CLI | CLI 以运维人员的身份、用运维人员自己的文件运行；文件里的每个目标本来就是他们的 |
| D-7 | 把租户与主体一并记录到运行上 | "这次是给哪个租户做的"是审计首先会问的问题，而事后从目标反推，等于假设配置从未变过 |

## 3. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| RSK-1 | 新增的端点返回了目标或运行记录却没做过滤 | 强制执行只存在于一个函数里，并由结构性测试断言没有任何处理函数自行比较租户 |
| RSK-2 | 开启租户打破了一个本来正常的单租户部署 | 它不可能被意外开启：必须有人把 tenant 写到某个目标上，此后加载时的规则会明确指出还需要做什么 |
| RSK-3 | 被过滤后的列表看起来像"资产为空"，有人因此去排查错误的方向 | `mas doctor` 会说明租户状态与每个凭据的触达范围，答案只有一条命令之遥 |
| RSK-4 | 拒绝通过时序或不同的状态码泄露了存在性 | 跨租户与"不存在"产生相同的错误码、相同的状态码与相同的响应体；有测试断言两者的响应完全一致 |

## 4. 实施顺序

1. 目标上的 `tenant`、凭据上的 `tenants`，以及加载时的规则。
2. 主体上的租户集合，以及回答那个问题的唯一函数。
3. 强制执行：诊断、目标列举、运行记录的列举与读取。
4. 运行记录上的租户。
5. `mas doctor`；双语文档。
