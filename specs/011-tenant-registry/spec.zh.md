# 特性规格：给目标与凭据加上租户维度

> **特性 ID**：`011-tenant-registry` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.2.1
> **宪法**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

特性 009 给 API 加上了凭据与两个 scope，并明确说明了它留下的缺口：
*一个可以做诊断的凭据，可以诊断任何已配置的目标*。
对于"一个团队照看自己那片资产"来说这没问题；
而对于"这片资产不属于某一个团队"的任何安排，这都是错的。

一个平台团队为若干产品团队运行同一个 MAS-Turbo。
今天，这些团队要么拿到一个"可以做诊断"的 token ——
从而也能读取其他每个团队中间件的遥测数据与已存储的诊断 ——
要么什么都拿不到，只能自己再跑一份：自己的凭据、
自己那份逐渐与所有人分叉的知识包，以及自己的账单。

同样的缺口也出现在一个组织内部 ——
只要存在一条"并非整个部署"的边界：同一份配置里的预发与生产、
一个受监管负载与一个不受监管负载并置、
一个面向客户的集群与一个内部集群并置。
在每一种情形下，运维人员想说的都是"这个凭据是给这些目标用的"，
而目前没有任何词汇能表达它。

`targets:` 是一个没有任何维度可供切分的扁平列表，
因此这首先是一次注册表的改动，其次才是一次授权的改动 ——
这也正是它成为独立特性、而不是对 009 的一次修订的原因。

## 2. 用户与场景

| 角色 | 目标 | 触发时机 |
|---|---|---|
| 平台工程师 | 用同一个部署服务多个团队，且任何一方都读不到另一方的遥测 | 接入第二个团队 |
| 团队工程师 | 恰好看到属于自己的那些目标，并确信这份列表不是被误过滤的 | 每天 |
| 审计人员 | 证明某个凭据不可能读到某个租户的运行记录 | 合规问询 |
| 单团队运维人员 | 完全不必学习这一套 | 每天 |

## 3. 范围

### 范围内
- 目标上的 `tenant`，以及 API 凭据上的 `tenants` 列表。
- **默认关闭租户**：没有任何地方写了 tenant 的配置，行为与今天完全一致。
- **一旦开启即默认拒绝**：只要有任何一个目标声明了 tenant，
  那么每个目标都必须声明，且每个凭据都必须声明它可以代表哪些租户。
- 在每一条会指名或返回目标的路径上强制执行：
  发起诊断、列举目标、列举与读取运行记录。
- 把租户与主体一并记录到运行上。
- `mas doctor` 报告租户状态，以及每个凭据能触达的范围。
- 双语错误与文档。

### 范围外
- 按租户配置其他任何东西：模型、预算、知识包、遥测数据源。
  每一项都是真实的诉求，也都需要各自的答案；
  一个会悄悄换掉模型的租户，是没有人要求过的意外。
- 按租户切分存储布局。运行记录仍存放在同一处，只是带上租户标记；
  切分桶是保留策略的决定，而不是访问控制的决定。
- CLI 上的租户。它以运维人员的身份、用运维人员自己的配置运行 ——
  文件里的每个目标本来就都是他们的。
- 委派、层级或分组。一组扁平的名字就好，
  因为"第一版就带层级的租户模型"，是没有人能推理清楚的租户模型。
- 配额或按租户的成本上限。它们值得有，但属于另一个关注点。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 目标可以声明 `tenant` | P0 | `TestTargetsCarryATenant` |
| FR-002 | 没有任何地方写 tenant 的配置，行为必须与之前完全一致 | P0 | `TestTenancyOffChangesNothing` |
| FR-003 | 只要有目标声明了 tenant，所有目标都必须声明，否则配置被拒绝 | P0 | `TestPartialTenancyIsRefused` |
| FR-004 | 租户开启时，未声明任何 tenants 的凭据必须在加载时被拒绝 | P0 | `TestCredentialWithoutTenantsIsRefused` |
| FR-005 | 对主体所属租户之外的目标发起诊断，必须以错误码被拒绝 | P0 | `TestDiagnosingAnotherTenantIsRefused` |
| FR-006 | 列举目标时只能返回主体所属租户的目标 | P0 | `TestTargetListingIsTenantScoped` |
| FR-007 | 列举与读取运行记录必须按租户限定 | P0 | `TestRunAccessIsTenantScoped` |
| FR-008 | 运行必须记录它属于哪个租户 | P0 | `TestRunRecordCarriesTheTenant` |
| FR-009 | 拒绝访问其他租户的目标时，不得泄露该目标是否存在 | P0 | `TestCrossTenantRefusalRevealsNothing` |
| FR-010 | 强制执行必须发生在单一收口点，而不是各个处理函数里 | P0 | `TestTenancyIsEnforcedInOnePlace` |
| FR-011 | `mas doctor` 必须报告租户状态与每个凭据的触达范围 | P1 | `TestDoctorReportsTenancy` |
| FR-012 | 凭据上出现未知租户，必须在加载时被拒绝 | P1 | `TestCredentialNamingAnUnknownTenantIsRefused` |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 租户一旦开启即默认拒绝 | 宪法第七条 |
| CON-002 | 单一收口点；任何处理函数都不得自行过滤 | 第七条第 2 款；特性 009 先例 |
| CON-003 | 拒绝不得泄露其他租户目标的存在性 | §1 |
| CON-004 | 每条消息都要有两种语言 | 第三条 |

## 7. 验收

当满足以下条件时，本特性完成：目标可以指定租户；
凭据可以指定它能代表哪些租户；对他人目标的请求会在不泄露其是否存在的前提下被拒绝；
各类列举只显示调用者可见的内容；运行记录写明它属于哪个租户；
且没有写任何 tenant 的部署丝毫未变。
