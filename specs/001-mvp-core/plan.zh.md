## 1. 技术上下文

| 方面 | 决策 |
|---|---|
| 语言 / 运行时 | **Go 1.24** —— 单一静态二进制、一等公民的并发、极小容器 |
| CLI 框架 | `spf13/cobra` |
| 配置 | `gopkg.in/yaml.v3` + 环境变量叠加 + 命令行叠加（自实现优先级，不引入框架） |
| 日志 | 标准库 `log/slog`（JSON 与文本 handler），自定义脱敏 handler |
| HTTP | 标准库 `net/http`（服务端与客户端）；不用 Web 框架 |
| Kubernetes 访问 | **专用只读 REST 客户端** 直连 apiserver —— 见 §6 |
| LLM 供应商 | 基于 `net/http` 手写客户端：Anthropic Messages API、OpenAI 兼容 Chat Completions，外加 `mock` |
| 自身指标 | 自实现 Prometheus 文本暴露格式（不引入客户端库）—— 见 §6 |
| 规则表达式 | `github.com/expr-lang/expr` —— 无外部依赖的表达式求值器，用于剧本条件 |
| 知识包 | YAML 数据文件，`go:embed` 内置默认 + 用户目录叠加 |
| 存储 | 文件系统运行存储，置于 `RunStore` 接口之后 |
| 测试 | `go test`、为每个外部系统提供 `httptest` 桩、黄金文件、对抗性安全套件 |
| 目标平台 | linux/amd64、linux/arm64；基于类 distroless 极小基础镜像 |

### 语言选型决策（回应 project-goals ASM-G3）

显而易见的反方意见是：多 Agent 生态以 Python 为中心（LangGraph、AutoGen、CrewAI）。本项目
选择 **Go**，理由是本系统的主要工作量并不在模型编排，而在于 *对运维系统进行并发、有界、安全的
I/O*，以及 *确定性规则求值*；模型调用只是相对薄的一层。

| 受力 | Go | Python |
|---|---|---|
| 以单一静态二进制 + 极小镜像交付（G12.1） | 原生支持 | 需要解释器与依赖；镜像大 5–10 倍 |
| 带逐调用超时的并发有界证据采集 | `context` + goroutine，符合语言习惯 | `asyncio` 可行，但把边界做对更费劲 |
| 可证明只读、可对抗性测试的强制机制 | 静态类型 + 单一受守卫调用路径 | 动态特性让守卫更容易被绕过 |
| 运维工具生态（K8s、Prometheus） | 原生主场 | 二等公民 |
| 多 Agent 框架可用性 | 需自建 | 丰富（LangGraph、AutoGen） |
| 拓扑实验（G7.3） | 基于自有注册表构建 —— *这本身是特性*，因为框架会强加自身执行模型，反而让同条件拓扑对比更困难 | 框架有帮助，但跨框架比较存在混杂因素 |

框架方面的差距真实存在，但很窄：LangGraph 中我们真正需要的东西 —— 一个带类型的状态对象、
一张步骤图、消息传递 —— 用 Go 写大约 700 行。而它**不提供**的是安全守卫、采集器与知识包，
而这些才是本系统的主体。自建编排层还让 G7.3 拥有干净的实验设计：状态相同、工具相同、证据相同，
只有拓扑不同。

**反转条件**（记录下来以保持该决策可被证伪）：若 M3 的评测显示我们正在大量重造框架能力
（结构化规划 DSL、学习型路由、记忆层级），则新增一个实现相同 `Orchestrator` gRPC/HTTP 契约的
Python sidecar，而不是重写内核。拓扑注册表正是让这件事无需触碰采集器、知识包与安全机制的接缝。

## 3. 阶段分解

| 阶段 | 产出 | 退出条件 |
|---|---|---|
| **A. 基础** | 错误、日志、配置、运行上下文、安全守卫 | 守卫对抗性套件全绿；`mas version` 可运行 |
| **B. 能力层** | 工具抽象；Prometheus、Loki、Kubernetes 采集器 | 每个采集器对其 `httptest` 桩全绿 |
| **C. 知识与规则** | 知识包 Schema、Redis + Kafka 包、剧本引擎 | 剧本运行在 `llm_calls == 0` 下产出结论 |
| **D. 推理层** | LLM 供应商、Agent 运行时、角色、`single` + `supervisor` 拓扑 | 同一请求在两种拓扑下均产出报告 |
| **E. 输出与持久化** | 报告模型、Markdown/JSON 渲染器、运行存储、重放 | 黄金文件测试；`mas replay` 复现报告 |
| **F. 操作面** | CLI、HTTP API、健康检查、自身指标、`doctor` | 冒烟与 API 测试全绿 |
| **G. 交付** | Dockerfile、GitHub Actions、手册、配置与错误码参考 | 镜像可运行；发布流水线产出制品 |

除 B 落地后 C 与 D 可并行外，顺序为严格依赖链。

## 5. 风险

| ID | 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|---|
| RSK-001 | 自研 Kubernetes 客户端处理鉴权（exec 插件、客户端证书）有误 | 中 | 高 | 支持 SA token、客户端证书、bearer token、exec 插件；`mas doctor` 精确探测并报告；每种鉴权方式均有单测 |
| RSK-002 | LLM 产出无法解析的工具调用，导致运行卡死 | 中 | 中 | 严格 Schema 校验、有界修复重试，其后确定性回退到仅剧本结论 |
| RSK-003 | Agent 循环空耗 token 而不收敛 | 中 | 中 | 硬性上限：最大步数、最大工具调用数、最大墙钟、最大 token；超限则输出已获结论并显式标注截断 |
| RSK-004 | 安全守卫存在绕过路径 | 低 | 严重 | 单一收口点；默认拒绝；对抗性测试套件；守卫不可被配置关闭 |
| RSK-005 | 知识包与现实脱节 | 中 | 中 | 知识包是带版本的数据且有一致性测试；每条结论都引用产生它的规则 ID |
| RSK-006 | 厂商遥测 API 差异（VictoriaMetrics 与 Prometheus） | 低 | 中 | 面向文档化的 v1 形态编程；厂商特异性隔离在采集器接口之后 |
| RSK-007 | 没有语料库就无法度量报告质量 | 高 | 中 | M1 接受该风险；M3 交付评测框架。M1 断言的是**结构性**质量（证据引用、无无支撑断言） |

## 6. 复杂度追踪

| 偏离项 | 为何必要 | 更简方案被否决的原因 |
|---|---|---|
| 用专用 Kubernetes REST 客户端替代 `client-go` | 为了我们只用到的约 6 个只读端点，`client-go` 会带来约 40 MB 与庞大的传递依赖；它同时引入远超我们白名单的 Schema 面，削弱 CON-002 | 依赖 `client-go` 因镜像体积（NFR-005）、审计面以及“窄客户端让只读保证可被检视”而被否决 |
| 自实现 Prometheus 指标暴露 | 序列数少于 15 条；客户端库的注册表/collector 机制完全用不上 | `prometheus/client_golang` 被否决：对这个面而言依赖代价高于收益 |
| 自建 Agent 编排层而非使用框架 | 见 §1；G7.3 的同条件拓扑对比要求如此 | 现有框架被否决，因为其执行模型会成为拓扑实验中的混杂因素 |
