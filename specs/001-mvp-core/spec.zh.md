## 1. 问题陈述

当一个 Redis 集群开始驱逐 key、一个 Kafka 消费组开始堆积、或者一个 MongoDB 主节点开始拒绝写入
时，运维人员的头三十分钟基本都花在**拼装上下文**上：打开 Grafana、猜一条合适的 PromQL、tail
Pod 日志、回忆这类故障该看 `INFO` 的哪个字段、确认线上版本是否踩了某个已知缺陷。真正需要专业
判断的分析部分，要等到这些拼装工作做完才开始，而且往往是在压力之下由当班的人来做，而不是由最
熟悉这套系统的人来做。

代价体现在故障定位平均耗时上、体现在本可避免的升级上、也体现在最终只记录了“重启了什么”而没
记录“到底哪里出了问题”的故障报告上。

目前没有一个工具能同时做到：(a) 自动汇集这些异构证据；(b) 对其套用中间件专属的专家知识；
(c) 展示自己的推理过程与证据；(d) 因为**可证明地无法触碰生产环境**而值得被指向生产环境。

## 2. 用户与场景

| 角色 | 目标 | 触发条件 |
|---|---|---|
| SRE / on-call 工程师 | 在几分钟内拿到对线上症状的、有证据支撑的排序解释 | 告警触发；执行 `mas diagnose` |
| 中间件平台工程师 | 把团队经验沉淀一次，让定位不再取决于谁在值班 | 编写/扩展知识包 |
| 支持工程师 | 在没有集群权限的情况下分析客户导出的遥测数据 | 对快照使用离线模式 |
| 应用型 AI 研究者 | 在完全相同的真实诊断 case 上比较多 Agent 拓扑 | 同一 case 分别跑 `single` 与 `supervisor` |

### 主要用户旅程
1. 运维人员在 `mas.yaml` 中一次性配置目标与遥测端点。
2. 告警触发：*“redis-prod-0 延迟 p99 上涨 8 倍”*。
3. 运维人员执行 `mas diagnose --target redis-prod --symptom "p99 latency spike" --since 1h`。
4. MAS-Turbo 解析目标、加载 Redis 知识包，先运行确定性剧本检查（内存压力、驱逐、fork 延迟、
   慢日志、连接抖动）。
5. 在确定性层无法定论之处，Agent 提出假设并请求进一步的定向证据 —— 特定的 PromQL 曲线、特定
   的 LogQL 时间窗、特定的只读 `INFO` / `CLIENT LIST` 巡检。
6. 批判 Agent 拿收集到的证据逐条挑战假设；缺乏支撑的假设被丢弃或降权。
7. 运维人员读到一份 Markdown 报告：带置信度的排序假设、每条假设的证据、检查过但正常的项、
   无法检查的项，以及带风险标注的建议性后续动作。
8. 该次运行被存档，可重放、可分享、也可换一种拓扑重跑。

## 3. 范围

### 范围内（M1）
- 诊断运行生命周期：请求 → 规划 → 证据采集 → 分析 → 批判 → 报告。
- 遥测采集器：Prometheus 兼容指标；Loki 兼容日志。
- 环境适配器：Kubernetes（只读 API 读取）与本地主机（白名单只读巡检命令）。
- 源码获取：网络仓库，并在网络不可用时自动回退到本地镜像，另含对已获取代码树的检索。
- 知识包：Schema + Redis + Kafka。
- 确定性剧本引擎，既可独立运行，也可作为 Agent 工具被调用。
- Agent 运行时，含五种角色；两种可互换拓扑（`single`、`supervisor`）。
- LLM Provider 抽象：`mock`、`anthropic`、`openai`（OpenAI 兼容端点）。
- 安全守卫：强制只读、默认拒绝、脱敏与资源上限。
- 错误码注册表、结构化日志、运行记录、重放。
- CLI 与 HTTP API；容器镜像；GitHub Actions 发布；双语用户手册。

### 范围外（M1 —— 是推迟，不是取消）
- Kubernetes 容器内命令执行（`exec` 子资源）（M2 · P1-1）。
- 本地目标自动发现与中间件配置文件解析（M2 · P1-1）。
- 深度源码分析：构建图、跨版本 diff、符号索引（M2 · P1-2）。
- MongoDB / Pulsar / Milvus / OceanBase 知识包（M2 · P1-3）。
- `plan-execute` / `debate` / `blackboard` 拓扑（M2 · P1-4）。
- 评测框架与 case 语料库（M3）。
- 认证、非文件系统的持久化存储、Web UI（M4）。
- project-goals §4 中的所有非目标 —— 本阶段永久排除。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 系统 MUST 接受包含目标、症状、时间窗口、模式与拓扑的诊断请求，并 MUST 以带错误码的方式拒绝非法请求 | P0 | 单元测试：合法请求受理；每个非法字段返回其文档化的 `MAS-1xxx` 码 |
| FR-002 | 系统 MUST 将目标名解析为中间件种类、版本（可发现时）、环境绑定与遥测标签选择器 | P0 | 解析已配置目标返回完整 `Target`；未知目标 → `MAS-1005` |
| FR-003 | 系统 MUST 查询 Prometheus 兼容端点的瞬时与区间序列，并遵守配置的鉴权、超时与结果规模上限 | P0 | 针对 httptest Prometheus 桩的集成测试，含鉴权头与截断 |
| FR-004 | 系统 MUST 查询 Loki 兼容端点在给定时间窗内的日志行，且结果条数有上限 | P0 | 针对 httptest Loki 桩的集成测试 |
| FR-005 | 系统 MUST 以只读 API 权限读取目标命名空间的 Pod、Pod 日志、事件与节点 | P0 | 针对 httptest Kubernetes API 桩的集成测试 |
| FR-006 | 系统 MUST 在调用到达任何外部系统之前，拒绝任何不在只读白名单内的工具调用 | P0 | 对抗性单元测试：变更类动词、变更类子命令、路径穿越、Shell 元字符，全部以 `MAS-8xxx` 拒绝 |
| FR-007 | 系统 MUST 从内置默认与用户指定目录加载中间件知识包，并按公开 Schema 校验 | P0 | 合法包可加载；每种 Schema 违规返回其 `MAS-5xxx` 码 |
| FR-008 | 系统 MUST 执行确定性剧本 —— 采集 → 评估 → 结论 的有序步骤 —— 且 LLM 调用次数为 0 | P0 | 剧本运行对 mock provider 记录 `llm_calls == 0` |
| FR-009 | 系统 MUST 支持至少两种可互换的 Agent 拓扑，按运行选择且无需改代码 | P0 | 同一请求在 `single` 与 `supervisor` 下由不同编排器产出报告 |
| FR-010 | 系统 MUST 支持至少两个 LLM 供应商加一个确定性 mock，由配置选择，并支持按 Agent 覆盖模型 | P0 | Provider 注册表测试；按 Agent 覆盖生效 |
| FR-011 | 系统 MUST 产出包含排序假设、逐条置信度与证据引用、已通过的检查、信息缺口、以及带风险标注的建议动作的报告 | P0 | 渲染器的 Markdown 与 JSON 黄金文件测试 |
| FR-012 | 系统 MUST 持久化可重放的运行记录：请求、计划、每次工具调用的参数与脱敏结果、每次模型交互、最终报告 | P0 | `mas replay <run-id>` 在无网络无模型的情况下复现报告 |
| FR-013 | 系统 MUST 在数据源不可用时降级：运行继续、缺口被记录、报告说明该缺口对置信度的影响 | P0 | 指标端点关闭时的测试：运行完成，报告列出缺口 |
| FR-014 | 系统 MUST 提供包含 `diagnose`、`serve`、`doctor`、`replay`、`errcodes`、`packs`、`topologies`、`version` 的 CLI | P0 | 每个子命令的 CLI 冒烟测试 |
| FR-015 | 系统 MUST 提供 HTTP API：创建诊断、获取结果、列出运行、健康检查与自身指标 | P0 | 每个端点的 `httptest` API 测试 |
| FR-016 | 系统 MUST 从日志、报告、运行记录与模型提示词中脱敏凭据与配置的敏感模式 | P0 | 脱敏测试在每个边界注入密钥并断言其不存在 |
| FR-017 | 系统 MUST 输出携带 `run_id` 的结构化日志，且 MUST 为每个跨边界错误附加 `MAS-NNNN` 码 | P0 | 日志捕获测试；边界错误审计测试 |
| FR-018 | 系统 MUST 支持按需校验配置并探测每个已配置端点，逐项报告状态与错误码 | P0 | `mas doctor` 对桩服务逐项报告状态 |
| FR-019 | 系统 SHOULD 按运行记录 token、成本、时延与工具调用次数 | P1 | 运行记录含已填充的 `Usage` 块 |
| FR-020 | 系统 MUST 提供以 CLI 为入口、可非 root 运行的容器镜像 | P0 | 镜像可构建；`docker run … version` 与 `… diagnose` 成功 |
| FR-021 | 系统 MUST 对本地主机做只读巡检 —— 进程存在性、监听端口、资源占用、白名单诊断命令 —— 以覆盖部署在 Kubernetes 之外的中间件 | P0 | 使用桩命令执行器的单元测试；对抗性测试确认非白名单命令被拒绝 |
| FR-022 | 系统 MUST 从网络仓库获取中间件源码，MUST 在网络不可用时自动回退到配置的本地镜像，并 MUST 报告实际使用了哪个来源 | P0 | 远端不可达时的测试断言发生了回退且被记录进运行记录 |
| FR-023 | 系统 MUST 在已获取的源码中检索字面串、符号与日志格式模式，使观察到的日志行可被定位到代码 | P0 | 对固定代码树的检索返回文件、行号与上下文 |

## 5. 非功能需求

| ID | 类别 | 需求 | 度量方式 |
|---|---|---|---|
| NFR-001 | 时延 | 使用 mock provider 与桩遥测的端到端诊断 < 5 秒 | 集成测试断言墙钟时间 |
| NFR-002 | 时延 | 一次确定性剧本运行 < 2 秒 | 测试断言墙钟时间 |
| NFR-003 | 安全 | 在任何输入（含对抗性输入）下，到达目标的变更类操作数为 0 | 对抗性测试套件 |
| NFR-004 | 资源边界 | 每次外部调用都有超时、响应大小上限与并发上限 | 每个采集器的单元测试 |
| NFR-005 | 可移植性 | linux/amd64 与 linux/arm64 的静态二进制；镜像 < 100 MB | CI 构建矩阵 + 镜像体积闸门 |
| NFR-006 | 可测试性 | 任何测试都不需要网络或真实模型 | CI 在禁出网环境下运行 |
| NFR-007 | 可扩展性 | 新增一种中间件只需一个知识包文件 | 仅通过知识包新增一种合成中间件的测试 |
| NFR-008 | 可观测性 | 日志结构化、可按 `run_id` 关联、级别可配 | 日志测试 |
| NFR-009 | 文档 | `docs/`、`specs/`、`.specify/` 双语对等度 100 % | CI 中的 `sddctl verify` |
| NFR-010 | 确定性 | 相同输入 + mock provider ⇒ 相同报告 | 重复运行相等性测试 |

## 7. 假设

| ID | 假设 | 若假设不成立 |
|---|---|---|
| ASM-001 | 目标在配置中声明；M1 不需要自动发现 | 新增发现类采集器（M2） |
| ASM-002 | Prometheus HTTP API v1 与 Loki HTTP API v1 的形态已足够 | 在同一接口后新增各厂商适配器 |
| ASM-003 | 可获得只读 Kubernetes 凭据（SA token 或 kubeconfig） | 仅离线模式可用；`mas doctor` 会报告此情况 |
| ASM-004 | 文件系统运行存储对 M1 足够 | 可插拔存储接口已隔离该问题（M4） |
| ASM-005 | 所配置的供应商支持 LLM tool-calling，或可用结构化输出模拟 | mock 与 OpenAI 兼容路径均覆盖模拟路径 |
| ASM-006 | 主机或镜像中可用 `git` 客户端以获取源码 | 源码能力经 `mas doctor` 报告为不可用；运行按 FR-013 降级 |
