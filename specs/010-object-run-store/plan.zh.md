# 实施计划：基于对象存储的共享持久化运行存储

> **特性 ID**：`010-object-run-store` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 思路

两个决策，而且都不是"该用哪个库"——因为没有库可用：
本项目的每一个特性都保持了 `go.mod` 未变，
而 S3 SDK 会是它可能引入的最庞大的一棵依赖树。

**签名。** SigV4 是一份带公开测试向量的规范，其全部内容不过是
HMAC-SHA256、SHA-256 与仔细的规范化 —— 全都在标准库里。
把它做错的结果是 `403 SignatureDoesNotMatch`，而不是一个安全漏洞：
我们是客户端，一个我们算错的签名，是服务端会拒绝的签名。
这使它成为少见的"手写才是负责任选择"的情形，
而本项目此前已为 RFC 6455 做过同一件事，理由相同。
那些测试向量，正是把"我们实现了一份规范"变成"我们正确地实现了它"的东西。

**在一个没有 append 的后端上，如何保住"只追加"。**
`RunStore` 契约要求：步骤一旦记录，绝不重写。
文件系统存储通过"读出、追加、整体写回"来遵守这一点 ——
而在对象存储上，这意味着每一个步骤都要 GET 一次再 PUT 整条运行记录，
并且只要两个写入者重叠，就会发生丢失更新。

对象存储原生的答案把它反了过来：**每个步骤一个不可变对象**。
没有任何东西被重写，因为没有任何东西被写第二次。
记录对象在开始时写一次、在结束时写一次，而它们之间的步骤各自成对象，按键有序。

这让契约被字面地满足，而不是靠约定；
并且还带来了文件系统存储所没有的东西：
一次在首尾两次写入之间被打断的运行仍然可读，因为那些步骤已经在那里了。
过去，一次崩溃会丢掉"最后一次成功的整体写入"之后的一切；
现在它只会丢掉那些根本还没被刷出去的内容。

代价是：读取一次**未完成**的运行需要一次 LIST。
而已完成的运行 —— 也就是绝大多数读取 —— 只需一次 GET，这就是 NFR-003。

## 2. 设计决策

| ID | 决策 | 理由 |
|---|---|---|
| D-1 | 依据规范手写 SigV4，仅用标准库 | 为了一个用一百行就能算出来的签名，引入本项目可能引入的最大依赖，不划算 |
| D-2 | 用公开测试向量证明 | "我们实现了一份规范"与"我们正确地实现了它"是两种不同的主张，而只有一种可被测试 |
| D-3 | 每个步骤一个不可变对象 | 在没有 append 的后端上字面地满足"只追加"，并消除了读-改-写及其丢失更新 |
| D-4 | 记录对象只在 Create 与 Finish 时写，而不是每步都写 | 每步整体写回都要各付一次 GET 与一次 PUT；两次写入既限住了成本，又标记了真正重要的两个状态 |
| D-5 | Get 优先读记录对象，读不到则退回重建 | 已完成的运行只需一次 GET；被中断的运行仍然可读 —— 而这是文件系统存储做不到的 |
| D-6 | List 使用键前缀与运行 id 自带的时间序 | 运行 id 形如 `run-<类 RFC3339>-<随机>`，因此字典序倒排**就是**最新优先 —— 无需维护索引，也就没有索引会与事实脱节 |
| D-7 | 凭据是 `Secret`，且只来自配置 | 实例元数据与 `~/.aws` 意味着多两条代码路径，以及多两种"搞不清用的是哪个身份"的意外 |
| D-8 | 存储失败是一个运行会报告的、带错误码的错误，绝不是静默丢弃 | CON-002。一条悄悄没保存上的记录，比一条大声失败的更糟 —— 因为在需要它之前没有人会去找它 |

## 3. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| RSK-1 | 签名有细微错误，对某个实现能用、对另一个不能用 | 公开测试向量覆盖了各实现之间会产生差异的规范化情形；桩服务端会真正校验签名，而不是忽略它 |
| RSK-2 | 两个副本写了同一个运行 id | 运行 id 带随机后缀，且一次运行写入的每个对象都在它自己的前缀之下；发生碰撞需要同一毫秒加上同一次随机抽取 |
| RSK-3 | 被中断的运行重建出某种具有误导性的东西 | 重建出的记录保持 `status: running`，不会被当作已完成呈现；有测试专门断言这一点 |
| RSK-4 | 随着桶变大，List 变成 O(全部) | 前缀列举受 `limit` 限制并提前停止；它绝不会读取一条自己不会返回的记录 |

## 4. 实施顺序

1. 先单独做 SigV4，对着公开测试向量。
2. 一个最小 S3 客户端：PUT、GET 与 LIST，基于 `net/http`。
3. 存储本体：对象布局，Create/Append/Finish/Fail。
4. Get（含重建）；List（最新优先、有上限）。
5. 配置、校验、`store.Open`，以及 doctor 探测。
6. 双语文档与部署示例。
