# 概要设计（HLD）：基于对象存储的共享持久化运行存储

> **特性 ID**：`010-object-run-store` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它位于何处

```
  service ──► store.RunStore ──┬─► Memory   进程内
                               ├─► FS       单机磁盘
                               └─► S3       一个桶，被所有副本共享
                                     │
                                     ├─ sigv4.Sign   依据规范，由其测试向量证明
                                     └─ net/http
```

`RunStore` 之上的一切都不变。这条缝自 M1 起就在那里，
而这是第一个真正按它的用途去使用它的后端 —— 这正是要点：
一个始终只有一种真实实现的持久化接口，只是一个主张，而这是对它的检验。

## 2. 对象布局，以及它为什么长成这样

契约要求：步骤一旦记录，绝不重写。
文件系统存储遵守这个承诺的方式，是每来一个步骤就整体重写一遍记录 ——
这在本地磁盘上没问题，而在对象存储上则在两个方面都是错的：
每个步骤都要为整条运行记录付出一次 GET 与一次 PUT，
并且两个写入者会悄无声息地覆盖彼此的更新。

于是布局把它反了过来。没有任何东西被重写，因为没有任何东西被写第二次：

```
  <prefix>/runs/<runID>/record.json      Create 时写入，Finish 时重写一次
  <prefix>/runs/<runID>/steps/0001.json  只写一次，此后不再写
  <prefix>/runs/<runID>/steps/0002.json
  …
```

记录对象在一次运行的生命中出现两次，而这两次都标记着真正重要的状态：
*这次运行开始了*，以及*这次运行结束了，报告在此*。
两者之间的一切，各自成为不可变对象。

这让"只追加"被字面地满足，而不是靠约定；
并且还带来了文件系统存储从未有过的东西：
一次在这两次写入之间被打断的运行**仍然可读**。
在磁盘上，一次崩溃会丢掉"最后一次整体写入"之后的一切；
而在这里，那些步骤在发生的当时就已经持久化了。

代价是：读取一次未完成的运行需要一次 LIST 加上每个步骤一次 GET。
已完成的运行 —— 几乎是全部读取 —— 只需一次 GET，而那才是值得优化的情形。

## 3. 签名，以及它为什么写在这里

本项目的每一个特性都保持了 `go.mod` 未变，
而 S3 SDK 会是它可能引入的最庞大的依赖 ——
只为一个由 HMAC-SHA256、SHA-256 与仔细规范化构成的签名，而这些全在标准库里。

之所以说这是负责任的手写而不是鲁莽的手写，在于失败的方向。
我们是**客户端**。一个我们算错的签名，是服务端会拒绝的签名：
失败模式是 `403 SignatureDoesNotMatch`，而不是"一个未授权请求成功了"。
并且规范附带测试向量，因此"我们实现了它"与"我们正确地实现了它"
可以是两种不同的主张，而只有第二种会被断言。

本项目此前为 RFC 6455 做过同样的判断，理由相同，证据形态也相同。

## 4. 当那个桶不在时会怎样

失败的存储绝不能悄悄失败。一条悄悄没保存上的运行记录，比一条大声失败的更糟 ——
因为在需要它的那一刻之前，没有人会发现它不见了，
而那一刻恰恰是在复盘某件已经出错的事情。

因此，每一次存储失败都是一个带错误码的错误，连同运行 id 记入日志并浮现出来。
但它不会摧毁分析：如果桶是在诊断**完成之后**才不可用的，
运维人员仍然会拿到他们的报告，并在旁边看到"未能持久化"的说明。
因为没能把答案归档就把答案一起丢掉，在故障处置中是错误的交易。

## 5. 刻意不做的事

- **不引入数据库。** 无论关系型还是嵌入式，每一种选项都是一个依赖，
  而手写一个，就是让"并不在写数据库的人"去写一个数据库。
  签名是带公开向量的一百行代码；存储引擎不是。
- **不做桶策略。** 加密、对象锁定、版本控制、生命周期与保留，
  都在配置桶的地方、由拥有桶的人来配置。在这里重新实现其中任何一项，
  都只会是第二份、更弱的副本。
- **不做迁移工具。** 把一个目录搬进桶，是搬目录的工具该做的事，而它们早已存在。
- **不共享进行中的状态。** 多个副本不会协同处理一次正在进行的诊断。
  它们共享的是已完成运行的记录 —— 而那正是审计轨迹的含义。
- **不使用环境隐式凭据。** 实例元数据与 `~/.aws` 意味着多两条路径，
  以及多两种"搞不清用的是哪个身份"的可能。在这里，凭据是配置 ——
  与本项目其他每一处一致。
