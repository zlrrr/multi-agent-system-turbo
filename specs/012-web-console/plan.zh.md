# 实施计划：只读 Web 控制台

> **特性 ID**：`012-web-console` · **版本**：1.0.0 · **状态**：已批准
> **双语对照**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 思路

整个设计都由一个决定推导出来：**控制台是 HTTP API 的客户端，不是它的第二套实现。**

控制台想要的一切，都已经是某个端点。运行列表是 `GET /api/v1/diagnoses`，单次运行是
`GET /api/v1/diagnoses/{id}`，它的轨迹是同一个端点加 `?steps=true`，目标、知识包、拓扑各有
各的。只要浏览器去调这些端点，授权器、scope 检查与租户过滤就会一字不差地作用在控制台上，
和作用在 `curl` 上完全一样 —— 因为那**就是**同一条代码路径。没有任何东西被新增信任，也不
存在第二个会忘记租户过滤的地方。

另一条路 —— 让服务端渲染器直接读 service —— 是多数控制台的做法，而在这里是错的形状。它需要
自己的授权、自己的租户过滤、以及每个类型自己的投影；而此后新增的第一个端点，就会在一处
被过滤、在另一处没有。特性 011 存在的原因，恰恰就是这一类错误太容易犯。

于是服务端的全部贡献就是：提供四个静态文件，外加回答一个 API 此前答不出来的问题（配置的是
哪种语言）。

由此有三个推论，每一个都是设计决定，而不是顺手为之：

**外壳是匿名的。** 浏览器导航到 `/ui/` 时没法带上 `Authorization` 头 —— 任何普通导航都不能。
于是只有两种选择：要么外壳不需要凭据即可获取，要么就得有一个登录端点去发 Cookie，而 Cookie
意味着会话、CSRF，以及第二套认证方案。外壳只是 HTML、CSS、JavaScript 和一张 UI 标签表：
它透露的关于环境的信息，不比 `/healthz` 已经透露的更多。所以外壳匿名提供，而它取回的数据不。

**凭据由人输入，只活在这个标签页里。** 用 `sessionStorage` 而不是 `localStorage`，关掉标签页
就结束；绝不进 URL，因为 URL 会进访问日志、浏览器历史和 Referer 头；绝不进 Cookie，因为
浏览器会自动附带的凭据，就是需要 CSRF 防护的凭据。

**报告正文是不可信的。** 摘要来自语言模型，日志片段来自环境。两者都不受我们控制，而只要
控制台把其中任何一份变成 HTML，它立刻就是一个存储型 XSS 的入口 —— 在中间件主机上，能写入
一行日志的人几乎就是所有人。所以控制台压根不从数据生成 HTML：每一个值都以 `textContent`
的形式进入页面，并由测试拒绝掉那些有可能做别的事的注入点。

## 2. 设计决策

| ID | 决策 | 理由 |
|---|---|---|
| D-1 | 控制台是 API 的客户端；不设服务端数据通路 | 一条授权路径、一处租户过滤；第二处一定会走偏 |
| D-2 | 外壳匿名，数据不匿名 | 导航带不了 Bearer 头，而外壳本身什么也没暴露 |
| D-3 | 不用 Cookie、不用会话、不设登录端点 | 没有 Cookie 就没有 CSRF 也没有会话存储，而 Bearer 方案已经存在 |
| D-4 | 只读：控制台不能发起诊断 | 它花 token、读生产；那种凭据不该待在浏览器标签页里 |
| D-5 | 不用 `innerHTML`、不用 `eval`；每个值都走 `textContent` | 报告正文本质上就是模型输出与环境日志文本 —— 天然不可信 |
| D-6 | 严格 CSP，因而没有内联脚本与内联样式 | 作为 D-5 之后的纵深防御，代价只是两个文件 |
| D-7 | 资源用显式白名单，而不是在 embed 上架文件服务器 | 默认拒绝：往目录里加一个文件不应等于把它发布出去 |
| D-8 | 字符串表放在 Go 里，以 JSON 提供 | 配对检查于是由 Go 测试完成（和错误码注册表一样），而不是让 Go 测试去读 JavaScript |
| D-9 | 哈希路由，单一外壳 | 服务端保持简单，而 fragment 里的 run id 永远不会进访问日志 |
| D-10 | 语言：浏览器猜测 → 服务端配置语言 → 阅读者的选择 | 每一步都比上一步更权威，而最后一句话属于读者 |
| D-11 | `server.ui.enabled`，默认开启 | 需要先发现一个配置项才能启用的控制台，等于没人用的控制台；加固部署仍然可以说不 |
| D-12 | 关闭时返回 `MAS-7016`，而不是干巴巴一个 404 | 手动敲进这个 URL 的运维，值得知道原因和该改哪个配置项 |

## 3. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| RSK-1 | 模型或日志文本在控制台里作为脚本执行 | 资源中不存在任何 HTML 注入点；`TestConsoleNeverUsesAnHTMLSink` 逐个扫描，且 CSP 无论如何都禁止内联与远程脚本 |
| RSK-2 | 控制台变成绕过租户或 scope 的通道 | 它自己没有数据通路；`TestConsoleServesNoEstateData` 断言资源路由只返回内嵌字节 |
| RSK-3 | 凭据经由 URL、日志或持久化存储泄漏 | 只用 `sessionStorage`，只走请求头；`TestConsoleKeepsTheCredentialOutOfURLsAndCookies` 扫描所有替代做法 |
| RSK-4 | 渲染出来的报告读起来比诊断本身更确定 | 缺口、"仅供参考"、未定价成本与截断都是一等内容，并由测试断言每一项都被引用 |
| RSK-5 | 对资源做结构性测试，证明力弱于浏览器测试 | 在 LLD 中明说这是已知边界，而不是含糊带过；所选不变量正是扫描真能判定的那些 |
| RSK-6 | 凭据被粘贴进一个以明文传输的页面 | `httpapi.Admit` 已经拒绝在无 TLS 且未声明代理的情况下把带凭据的 API 绑到非本机；控制台再在非安全来源上额外给出警示 |
| RSK-7 | 字符串走样：被引用却不存在，或存在却没人引用 | `TestConsoleStringsAreAllUsed` 双向检查 |

## 4. 实施顺序

1. Go 中的字符串表及其配对测试。
2. 资源：外壳、样式表、脚本。
3. 提供服务：白名单、CSP、关闭路径、`MAS-7016`。
4. 结构性测试：HTML 注入点、凭据处理、渲染的诚实性。
5. 索引上的 `language`；`mas doctor`；双语文档。
