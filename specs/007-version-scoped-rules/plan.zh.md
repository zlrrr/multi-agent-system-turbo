# 实施计划：版本区间限定的知识包规则

> **特性 ID**：`007-version-scoped-rules` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 思路

机制本身很小。真正让这个特性值得设计而不只是"写出来"的原因是：
有三种看似都行的形态，其中两种会腐坏。

**形态 1 —— 每次查找时过滤。** 给 `Signal(id)`、`MatchingPlaybooks`、
`MatchLogPatterns`、`FailureMode` 与 `InspectCommands` 各加一个版本参数，各自内部过滤。
否决：有五个地方必须记得这件事，传入 `""` 的调用方会悄悄拿到未限定的行为，
而且今后每一个新的消费者都继承了这份义务。本项目已经四次遇到同一类缺陷 ——
某个授权或限定规则依赖调用方主动做点什么 —— 而每一次的修复都是"把选择权拿掉"。

**形态 2 —— 解析成一个新类型。** `Pack.Resolve(v) *ResolvedPack`，
只有 `*ResolvedPack` 才有那些访问方法，于是把未解析的包传给引擎会是编译错误。
保证最强，但因代价被否决：service、规则引擎、智能体提示词与 CLI 中
每一处提到 `*knowledge.Pack` 的签名都要改，而换来的性质用一个测试就能断言。

**形态 3 —— 解析成同一个类型，在准入阶段做一次。** `Pack.Resolve(v)`
返回一个切片已被过滤、元数据中记录了"为哪个版本解析"的 `*Pack`。
调用点无需改动。service 解析一次，本次运行的其余部分都用这个结果。
一个结构性测试断言 service 只经由已解析的包访问 playbook；
而对未做版本限定的包来说 `Resolve` 是恒等变换，因此语料库本身就是回归证明。

我们采用形态 3。它以形态 2 的零改造代价换来了它绝大部分的保证，
而让出的那部分保证由测试而不是类型系统兜住 ——
这正是本代码库在护栏的"唯一授权者"性质上已经做过的同一笔交易。

## 2. 设计决策

| ID | 决策 | 理由 |
|---|---|---|
| D-1 | 每类规则一个可选的 `versionRange` 字段，语法与包级的相同 | 第二套语法就是第二个解析器，以及第二套会犯的错 |
| D-2 | 每次运行解析一次，在准入阶段，而不是每次查找 | 只有这样才能做传递式丢弃；逐次查找的过滤看不到"谁依赖了它" |
| D-3 | 仅在区间互不重叠时允许重复 id | 这正是表达"改名"的方式。没有它，一次改名就会逼出第二个知识包 |
| D-4 | 重叠在加载时检查，而不是解析时 | 一个对**某些**版本存在歧义的包，对所有人来说都是坏的；而在故障处置中才发现是最糟的时机 |
| D-5 | 版本未知时丢弃变体并记录缺口 | 挑第一个变体，等于用一个可能根本不存在的指标名去回答，还把它称作测量。拒绝并说明，是唯一诚实的选项 |
| D-6 | 版本未知时**保留**只声明了一次的限定规则 | 一条超出区间的规则读到的是不存在的指标，引擎已经会把它记为缺口。把它也丢掉，只会白白失去一次本可做到的检查 |
| D-7 | 丢弃沿 signal → step → 槽位 → playbook 传递 | `x` 被丢弃后仍引用 `{{signal:x}}` 的步骤会在运行时报错；读取"没有存活步骤产出"的槽位会导致未定义变量错误。两者是同一个错误，只是被提前到加载时而不是凌晨三点 |
| D-8 | 每一次丢弃都是一条缺口，绝不静默省略 | CON-002。语料库已经证明：被静默跳过的检查会被读成"通过了的检查" |
| D-9 | 内置知识包中，只对版本边界有据可查的规则做限定 | 一个凭印象编出来、看上去合理的区间，比没有区间更糟：它会悄悄移除一条本来有效的检查 |

## 3. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| RSK-1 | 传递式丢弃删掉了不该删的，一次诊断悄悄失去了若干检查 | 每次丢弃都是一条带规则 id 的缺口；测试断言被丢弃 signal 的依赖方会被逐一列出 |
| RSK-2 | 重叠判定有误，一次真实的改名被拒绝 | 重叠在区间上计算，并带保守偏置：不确定时判为重叠。误拒是作者立刻会看到的加载错误；误收则是没有人会看到的歧义 |
| RSK-3 | 某处忘了解析，版本限定被绕过 | 结构性测试（FR-012）；已解析包上的 `resolvedFor` 让这件事可被观测 |
| RSK-4 | 内置知识包依据半记半忘的"事实"被限定 | 见 D-9：只用有据可查的边界，且我们发布的那一条由 case 语料库覆盖 |

## 4. 实施顺序

1. 每类规则加上 `versionRange`，完成解析与校验，行为不变。
2. 加载时的重叠检测与变体规则。
3. `Resolve`，含传递式丢弃与缺口。
4. service 解析一次；结构性测试。
5. Kafka 的 ZooKeeper 与 KRaft 边界；两侧各一个语料库 case。
6. `mas packs --show --version`；双语文档。
