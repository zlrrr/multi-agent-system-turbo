# 特性规格：版本区间限定的知识包规则

> **特性 ID**：`007-version-scoped-rules` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.1.6
> **宪法**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

目标 G2.3 要求：知识包中的规则可以被限定到某个版本区间。而今天被限定的只有
**整个知识包**：`metadata.versionRange` 决定整份文档是否适用，
文档内部的一切则无条件适用。

对于中间件真实的演进方式来说，这个粒度是错的。Kafka 4.0 移除了 ZooKeeper，
于是知识包里每一条 ZooKeeper 日志模式，都会对着一个根本没有 ZooKeeper 的集群去匹配 ——
匹配不到还算好的，匹配到某个无关组件的日志行才是坏的。Kafka 3.3 引入了 KRaft 的 raft 指标，
它们在此之前并不存在，因此一条读取这些指标的检查跑在 3.2 上时，
查询的是该部署从未导出过的指标。自特性 002 修复引擎之后，
这会被记为缺口而不是被读成 0 —— 这很诚实，但仍然是错的：
它为一条本就不适用的检查报告了"我们没能检查这个"。

唯一的绕行办法，是按版本区间把整个知识包复制一份。六个包变成十二个，
每一个共享的 signal 都被复制一遍，而下一次修订必须改两处 —— 知识就是这样开始分叉的。

底下还有第二个问题。中间件会改名字。同一个概念 ——"controller 是否健康"、
"这个租户用了多少内存"—— 在不同大版本中会以不同的指标名导出。
而一个 signal 只能有一段 PromQL，于是一次改名就逼出第二个知识包、
一个不同的 id，并且每一个引用过该 signal 的 playbook 也都得复制一遍。

## 2. 用户与场景

| 角色 | 目标 | 触发时机 |
|---|---|---|
| 知识包作者 | 把某条检查限定到它真正适用的版本，而不必分叉整个包 | 某个版本移除或新增了一个子系统 |
| 知识包作者 | 让一个 signal 在改名前后拥有两段表达式 | 某个大版本重命名了指标 |
| 使用旧版本的 SRE | 不再看到那些本就不适用于自己部署的检查所产生的缺口 | 任何一次诊断 |
| 未配置版本的 SRE | 被明确告知"与版本相关的知识被跳过了"，而不是悄无声息地丢失 | 对未配置版本的目标做诊断 |

## 3. 范围

### 范围内
- 知识包内每一类规则都可选声明 `versionRange`：signals、logPatterns、
  failureModes、playbooks、playbook 的 steps，以及 inspect 命令。
- **变体**：同一个规则 id 可以在区间互不重叠的前提下声明多次，解析时选中适用的那一个。
- 每次运行**只解析一次**，依据目标的版本，产出本次运行其余部分所看到的知识包。
- **传递式丢弃**：依赖于被丢弃 signal、故障模式或槽位的步骤会一并被丢弃，
  而不是在运行时报错。
- 只要跳过了与版本相关的知识，就记录一条缺口，说明跳过了什么、以及为什么。
- 双语文档与错误码。

### 范围外
- 版本**发现**。版本仍然来自配置或环境适配器，与今天一致。
- 除中间件版本以外的任何区间维度 —— 不按部署形态、云厂商或 exporter 版本限定。
  每一种都需要自己的一套词汇，而 exporter 的版本尤其不等于中间件的版本。
- 重写现有知识包。本特性交付的是机制，以及那些版本边界有据可查的规则；
  对既有知识做大规模版本切分属于知识包工作，而不是代码工作。
- 会"猜"的解析器。当版本未知且某条规则存在变体时，本次运行会如实说明，而不是挑一个。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 知识包中的每一类规则都可以声明 `versionRange`，语法与 `metadata.versionRange` 相同 | P0 | `TestEveryRuleKindAcceptsAVersionRange` |
| FR-002 | 解析时必须丢弃区间不包含目标版本的规则 | P0 | `TestOutOfRangeRulesAreDropped` |
| FR-003 | 当每一次声明都带有区间、且任意两个区间互不重叠时，同一个规则 id 可以声明多次 | P0 | `TestVariantsWithDisjointRangesAreAccepted` |
| FR-004 | 同一 id 上出现重叠区间，必须在加载时拒绝，并指出是哪两个 | P0 | `TestOverlappingVariantsAreRejected` |
| FR-005 | 解析必须选中区间适用于目标版本的那个变体 | P0 | `TestVariantMatchingTheVersionIsChosen` |
| FR-006 | 版本未知时，带变体的规则必须被丢弃并记录缺口，而不是被猜测 | P0 | `TestUnknownVersionDropsVariantsWithAGap` |
| FR-007 | 引用了被丢弃 signal 或故障模式的步骤，必须随之被丢弃 | P0 | `TestStepsFollowTheRulesTheyDependOn` |
| FR-008 | 表达式读取了"没有任何存活步骤产出"的槽位的步骤，必须被丢弃 | P0 | `TestStepsFollowTheSlotsTheyRead` |
| FR-009 | 若某个 playbook 已不剩任何能抵达结论的步骤，必须整体丢弃 | P0 | `TestEmptyPlaybooksAreDropped` |
| FR-010 | 每一次丢弃都必须产生一条缺口，带错误码、被跳过的内容及其对分析的影响 | P0 | `TestSkippedRulesAreRecordedAsGaps` |
| FR-011 | 解析绝不得放宽任何东西：任何规则、任何 inspect 命令，都不得对其区间排除的版本变为可用 | P0 | `TestResolutionNeverWidens` |
| FR-012 | 一次诊断必须使用已解析的知识包，使版本限定无法因某个调用方遗忘而被绕过 | P0 | `TestDiagnosisUsesTheResolvedPack` |
| FR-013 | `mas packs --show` 必须显示规则的区间，并支持传入版本以预览解析结果 | P1 | `TestPacksCommandShowsVersionScoping` |
| FR-014 | 内置 Kafka 知识包必须对那些版本边界有据可查的规则做限定 | P1 | `TestKafkaPackScopesZooKeeperRules` |

## 5. 非功能需求

| ID | 需求 | 度量 |
|---|---|---|
| NFR-001 | 解析每次运行只发生一次，而不是每次查找都做一次 | 结构性测试 |
| NFR-002 | 不引入新的模块依赖 | `go.mod` 未变 |
| NFR-003 | 每一条面向运维人员的字符串都是双语 | `sddctl verify` |
| NFR-004 | 未做版本限定的知识包，其行为必须与今天完全一致 | 语料库原样通过 |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 解析只能收紧；无论如何都不影响安全护栏的白名单 | 宪法第七条 |
| CON-002 | 被跳过的知识是一条缺口，绝不是一次静默省略 | 第九条；design-lld.zh.md §2.12 |
| CON-003 | 规则仍然是数据：加上一个区间不需要重新编译 | G2.1 |
| CON-004 | 每条消息都要有两种语言 | 第三条 |

## 7. 验收

当满足以下条件时，本特性完成：知识包可以把任意规则限定到某个版本区间；
一次改名可以表达为同一个 id 的两个变体；对配置了版本的目标做诊断时，
看到的恰好是适用的那些规则；对未配置版本的目标做诊断时，会被告知失去了什么；
任何一次解析都不会放宽可执行的范围；且语料库原样保持绿色。
