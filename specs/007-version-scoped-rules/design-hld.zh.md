# 概要设计（HLD）：版本区间限定的知识包规则

> **特性 ID**：`007-version-scoped-rules` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它位于何处

```
  配置 / 环境适配器              知识库                              运行
  ─────────────────              ──────                              ────
  target.version  ────────────► Library.For(kind, version)
                                      │   （今天：包级区间）
                                      ▼
                                Pack.Resolve(version)  ──────────► *Pack（已解析）
                                      │                                │
                                      │ 缺口：跳过了什么                │
                                      ▼                                ▼
                                 report.Gaps                      规则引擎
                                                                  智能体提示词
                                                                  inspect 命令
```

新增的只有一条箭头：`Resolve`。它下游的一切都不变，因为它返回同一个类型。
这正是要点 —— 版本限定是"本次运行所持有的那个包"的属性，
而不是每个消费者都必须记得传的一个参数。

有两件事只发生在这条箭头上，别处都不发生：

- **收紧。** 被该版本排除的规则离开知识包。
- **记账。** 没有任何东西可以不被报告提及就离开。但并非每一次离开都值得同样的音量，
  而把这件事搞错，正是"缺口清单"沦为运维人员习惯性略过之物的方式 —— 见 §3.1。

## 2. 为什么这个边界是"解析"而不是"过滤"

过滤回答的是"这条规则适用吗"，一次一条。这对 signal 和日志模式够用，
对任何"有依赖方"的东西都不够。

一个 playbook 步骤读取 `{{signal:brokers}}`。若该版本下 `brokers` 被丢弃，
这个步骤就无法展开 —— 它会在运行时、在诊断进行到一半时，抛出一个模板错误。
这个步骤必须一并丢弃。后面还有一个步骤在求值 `brokers.min < brokers.max`；
一旦采集步骤被丢弃，这个表达式读到的就是一个没有任何东西产出的槽位。
它也必须一并丢弃。删掉足够多的步骤后，一个 playbook 可能再也无法抵达任何结论；
那时它就是一个"采集了证据却什么也不判定"的 playbook ——
既花掉了查询，又只返回发现而没有结论。

因此，解析的单位是知识包而不是规则：只有持有整份文档的东西，才能顺着这些边走。
这些边是：

```
  signal ──被引用于──► step ──产出槽位──► step ──►  ...
                        │
  failureMode ──被结论于─┘
                        │
                        └──► playbook（当不再剩下任何结论时丢弃）
```

解析按这个顺序走一遍，且每一次移除都指出是哪条规则导致的。

### 3.1 两种音量，因为它们是两件不同的事

一条不适用于所部署版本的规则，**不是**缺失的证据。这项检查在这里从来就不可能做；
什么也没有失去。把它们逐条列出，会让一个限定得当的知识包在缺口清单里塞进十几条，
而一旦运维人员学会了"缺口大多是噪音"，他们就会漏掉真正重要的那一条。
因此，所有这类情况 —— 区间排除了该版本的规则，以及由它们级联出的一切 ——
每次运行只汇总为**一条**缺口，写明版本并列出这些 id。

无法**定位**的规则则不同。当一个 id 存在变体、而目标又没有版本时，
确实存在一项本可执行却没有执行的检查，而运维人员用一行配置就能修好它。
这类情况每一条都拥有自己的缺口，并以那一行配置作为处置建议。
另一种情况同理：某个知识包的变体中没有任何一个适用于所部署的版本 ——
那是知识包自身的缺陷，而能修它的人需要看到是哪个 id。

规则是：**由"知道版本"推出的，汇总；由"不知道版本"推出的，逐条列出。**

## 3. 变体，以及唯一一处我们拒绝作答的情形

当每一次声明都带区间、且任意两个区间互不重叠时，一个规则 id 可以出现多次。
改名就是这样表达的：

```yaml
signals:
  - id: controller_count
    versionRange: "<3.3"
    promql: 'sum(kafka_controller_kafkacontroller_activecontrollercount{{.selector}})'
  - id: controller_count
    versionRange: ">=3.3"
    promql: 'sum(kafka_controller_kafkacontroller_activecontrollercount{{.selector}})'
```

所有 playbook 继续引用 `controller_count`。一份文档、一个 id、两段表达式，
由本次运行按版本挑选。

有意思的是**未配置版本**的目标。今天，版本缺失意味着"处处适用"，
对包级区间来说这是正确的默认：在故障处置中因为缺一个版本字符串就拒绝帮忙，是错误的交易。
但对**变体**来说，这根本不是什么默认值 —— 没有可回退的规则，只有二选一，
而选错就意味着去查询一个并不存在的指标名，并把它的"查不到"当成数据来读。

因此变体是本设计中唯一一处拒绝作答的地方：没有版本，该 id 就被丢弃，并由缺口说明原因。
那条缺口给出的处置只有一句话 —— 设置 `targets[].version` ——
运维人员据此就能行动。而一个猜测是无法据以行动的，因为没有人会知道它发生过。

只声明了一次的限定规则则不同：版本未知时它会被**保留**。这里没有什么需要在二者间抉择；
如果它其实并不适用，它的查询会什么都查不到，而引擎已经会把这记为缺口。
把它也丢掉，等于用"一次本可做到的检查"换来"完全没有信息"。

## 4. 解析绝不得做的事

解析只收紧。它没有任何一条分支会新增规则，尤其没有任何一条会新增 inspect 命令 ——
因为 inspect 是唯一一类会触达在线系统的规则。安全护栏无论如何都不受影响 ——
它在调用时会对着一份任何知识包都无法放宽的白名单重新校验每一条命令 ——
但"反正护栏会拦住"，不构成"去建造一个需要被拦住的东西"的理由。
一个测试断言：对任意版本，已解析包中的规则都是未解析包中规则的子集。

## 5. 刻意不做的事

- **不做版本发现。** 版本来自配置或适配器。去嗅探它，就是又一次在线调用、
  又一件可能弄错的事。
- **不按其他维度限定。** 部署形态、厂商、exporter 版本都是真实存在的维度，
  但它们都不是中间件的版本。把 exporter 的命名与中间件的版本混为一谈，
  是最诱人也最错误的一种做法。
- **不重写内置知识包。** 机制随那些边界有据可查的规则一同发布。
  一个凭印象编出来的区间会悄悄移除一条有效的检查，
  这比它想修的那个缺口更糟。
