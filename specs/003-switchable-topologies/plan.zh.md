# 实施计划：可切换的多 Agent 拓扑

> **特性 ID**：`003-switchable-topologies` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 思路

注册表、`agent.State` 与角色运行器都已存在，且当初就是为此而建。
因此这项工作几乎全部落在 `internal/orchestrator` 内部，外加新控制流真正需要的那几个 Agent 角色。

顺序是刻意的，与特性 002 一致：**一致性契约先写，并且要先用一个刻意做坏的拓扑证明它会失败，
然后才动手写任何真实拓扑。** 事后补写的契约只会把这三个拓扑碰巧做了什么编码下来，
那等于什么都没度量。这是本特性中最重要的一个排序决策 ——
因为可切换拓扑的全部意义就在于可比性，而可比性恰恰是那种会静默腐化的性质。

### 1.1 拓扑可以做什么、不可以做什么

拓扑是**角色之上的控制流**。它可以决定谁行动、按什么顺序、行动几次、在什么条件下行动。它不可以：

- 触及本次运行没有放进它所获注册表的工具；
- 绕过 `agent.State` 写入报告；
- 改变某个角色**是什么**（角色的提示词与契约归 `internal/agent` 所有）。

这条界线正是让比较有意义的关键：若拓扑之间可以在能力上有差异，
那么结果上的差异就无法归因于架构本身。

## 2. 设计决策

| ID | 决策 | 理由 | 反转条件 |
|---|---|---|---|
| D-1 | 一致性契约先行，并用一个刻意做坏的拓扑验证它确实会失败 | 从实现反推出来的契约度量不了任何东西 | — |
| D-2 | 不修改 `agent.State` | 每个拓扑的工作记忆（一份计划、一组立场）是它自己的局部数据；放进共享状态等于把某一个拓扑的模型泄漏给全部拓扑 | 当第二个拓扑确实需要把同一结构**持久化**进报告时 |
| D-3 | 新增四个角色：`Strategist`、`Executor`、`Advocate`、`Judge` | 每个都是独立契约，而不是既有角色的换参。`Planner` 只写一次散文式计划，供人阅读、也供调查员作为上下文；而自适应重规划是另一种契约 —— 结构化、迭代、会终止 —— 因此它应当是一个新角色（`Strategist`），而不是被重载的 `Planner`。`Executor` 执行一个既定目标；`Advocate` 为并非自己所选的立场辩护；`Judge` 在论证之间做出裁决 | 当第五个拓扑无需新增角色即可复用它们时 |
| D-4 | blackboard 的控制是确定性的，而非模型驱动 | 经典设计由控制组件判定哪个知识源具备条件。把这个判断交给模型，每轮多一次调用且破坏可复现性；"是否具备条件"本就是黑板状态上的一个谓词，用代码表达更好 | 当某个具备条件的判断确实需要谓词无法表达的语义时 |
| D-5 | 注册表中的拓扑描述改为双语 | FR-010 要求使用运维人员的语言；在双语产品里留一段纯英文描述，是对等性检查看不见的缺陷 —— 因为它不读 Go 代码 | — |
| D-6 | debate 争论的是 correlator 产出的假设，而不是 advocate 自行发明的立场 | 立场必须扎根于同一份证据，否则辩论只是表演 | — |
| D-7 | advocate 并发运行，笔记按确定顺序重排 | 与 supervisor 的 investigator 同理：独立 I/O 是主要开销，而 CON-003 由测试强制 | — |

## 3. 风险

| ID | 风险 | 缓解 |
|---|---|---|
| RSK-001 | 新拓扑更贵却并不更好，而工具通过"发布了它"暗示了相反的结论 | 描述中写明成本画像与**何时不该**选它；CON-002 禁止本特性给出其无法支撑的打分结论 |
| RSK-002 | `plan-execute` 反复循环却不收敛 | 硬性轮数上限，外加本次运行既有的步数预算；截断会被记录而非隐藏 |
| RSK-003 | `debate` 因某个 advocate 论证有力而虚高置信度 | 由裁决者对照证据裁定；一致性契约要求已被推翻的立场必须仍然是"已推翻" |
| RSK-004 | `blackboard` 不终止，或者一上来就终止 | "具备条件"的工作量必须严格递减；某一轮没有任何贡献即结束循环，契约对两端都做测试 |
| RSK-005 | 五个拓扑 × mock provider 的脚本回复会让测试变脆 | mock 按角色而非按调用序号驱动，因此改动一个拓扑不会把另一个拓扑的期望整体错位 |
