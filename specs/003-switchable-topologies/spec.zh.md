# 特性规格：可切换的多 Agent 拓扑

> **特性 ID**：`003-switchable-topologies` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.1.1
> **宪法**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

项目目标要求多 Agent 架构可切换，从而让"选哪种架构"由实验来定，而不是由口味来定。
承载这一点的注册表接缝已经存在，并由两种拓扑在使用 —— `supervisor`（默认）与
`single`（对照组）—— 但两个点连不成比较，而其中一个还是刻意退化的。

缺的不是接缝，而是接缝上没有插入足够有意思的东西。多 Agent 领域真正在争论的三种架构 ——
自适应的 plan/execute 循环、对抗式的 debate、机会驱动的 blackboard —— 与 `supervisor`
的差别正在于**控制流**，而这恰恰是运维人员想拿自己的故障案例去检验的那个变量。

还有第二个更隐蔽的缺口：今天没有任何东西强制一个新拓扑必须与既有拓扑**可比**。
一个悄悄跳过了批判环节、或者无法离线运行、或者输出取决于 goroutine 调度顺序的拓扑，
照样能注册、照样能跑 —— 而所有涉及它的比较都会毫无意义，且没人会察觉。
在没有先写下"什么才叫可比"之前就新增三个拓扑，只会把这个风险乘以三。

## 2. 用户与场景

| 角色 | 目标 | 触发 |
|---|---|---|
| SRE | 得到一次控制流与故障相称的诊断：可能一查即中时用自适应，两个原因长得很像时用对抗式 | 执行 `mas diagnose --topology …` |
| 平台工程师 | 基于本组织自己的故障证据，为团队选定默认拓扑 | 评估该工具时 |
| 研究者 | 固定其余一切，只改架构再做比较 | 研究多 Agent 设计 |
| 维护者 | 新增拓扑而不会静默破坏可比性 | 贡献代码时 |

## 3. 范围

### 范围内
- 一份**先于**新拓扑写就的拓扑一致性契约，所有已注册拓扑都必须满足。
- `plan-execute`：一个自适应循环，规划、每次执行一个目标、再依据所学重新规划。
- `debate`：由若干相互竞争的立场基于同一份证据展开论证，并由裁决者判定。
- `blackboard`：机会驱动、由数据决定控制流 —— 当共享状态使某个贡献者具备条件时它才行动。
- 上述拓扑真正需要的 Agent 角色，且仅限于此。
- 可供运维人员对比的按运行成本核算：模型调用数、工具调用数、token 与墙钟时间 ——
  这些已在记录，此处按拓扑呈现出来。
- 何时该选哪种拓扑的双语说明。

### 范围外
- Case 语料库与打分式评测框架（M3、P2-1）。本特性让比较**成为可能且公平**；
  在语料库上打分是另一项工作。
- 按 Agent 的模型路由（M2、P1-5）—— 与本特性正交，混在一起只会污染本特性想促成的那场比较。
- 修改 `supervisor` 或 `single`，除非一致性契约在它们身上暴露出真实缺陷。
- 任何新工具、采集器或环境访问。拓扑之间的差异在控制流，不在能力。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 每一个已注册拓扑都必须满足同一份一致性契约；未被该契约收录就发布的拓扑必须让构建失败 | P0 | `TestEveryRegisteredTopologyIsGoverned` |
| FR-002 | 系统必须提供 `plan-execute` 拓扑，并依据每个已执行目标的返回结果重新规划 | P0 | `TestPlanExecuteReplansOnFindings` |
| FR-003 | 系统必须提供 `debate` 拓扑：至少两个立场基于同一份证据论证，并由一个独立角色裁决 | P0 | `TestDebateProducesAdjudicatedPositions` |
| FR-004 | 系统必须提供 `blackboard` 拓扑，其控制流由共享工作区的状态驱动，而非固定脚本 | P0 | `TestBlackboardSchedulesByEligibility` |
| FR-005 | 在证据足以支撑结论时，每个拓扑都必须产出至少一条假设与一段摘要 | P0 | 一致性契约，逐拓扑执行 |
| FR-006 | 每个拓扑都必须把每一次模型交互归属到发起它的角色 | P0 | 一致性契约，逐拓扑执行 |
| FR-007 | 每个拓扑都必须遵守本次运行的步数预算，超限时记录截断而不是越界执行 | P0 | `TestTopologiesRespectStepBudget` |
| FR-008 | 某个工具域不可用时，每个拓扑都必须仍能完成，并记录缺口而非失败 | P0 | `TestTopologiesDegradeWithoutTools` |
| FR-009 | 同一拓扑在同一状态上跑两次，必须产出顺序一致的相同假设与笔记 | P0 | `TestTopologiesAreDeterministic` |
| FR-010 | `mas topologies` 必须以运维人员的语言描述每个拓扑，并说明何时优先选它 | P1 | CLI 测试断言全部名称与两种语言 |
| FR-011 | 运行记录必须标明产出它的拓扑及其按拓扑的成本 | P1 | `TestRunRecordCarriesTopologyAccounting` |
| FR-012 | 选择未知拓扑必须在任何模型调用之前以 `MAS-3001` 失败 | P1 | 扩展既有准入测试 |

## 5. 非功能需求

| ID | 需求 | 度量 |
|---|---|---|
| NFR-001 | 任何拓扑都不得访问本次运行未授予它的工具 | 结构审计测试 |
| NFR-002 | 新增拓扑不得需要修改 `internal/agent` 的状态或 service | 评审时的 `git diff`；契约测试 |
| NFR-003 | 一致性契约必须在确定性 mock provider 上运行，不触网 | `go test ./internal/orchestrator/...` 离线 |
| NFR-004 | 本特性新增的每一个面向运维人员的字符串都必须双语 | `sddctl verify` 对等检查 |
| NFR-005 | 拓扑不得放宽安全护栏，也不得触及所授注册表之外的工具 | 结构审计测试 |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 始终只读：拓扑只能引发只读工具调用 | 宪法第四条 |
| CON-002 | 本特性只做"比较"，不做"打分" —— 没有语料库就下打分结论，是无依据的断言 | 第九条，如实报告 |
| CON-003 | 拓扑内部的并发不得改变其输出 | FR-009 |
| CON-004 | 不引入新依赖 | 第七条第 4 款 |

## 7. 验收

当五个拓扑均已注册、五者都满足同一份一致性契约、`mas topologies` 以两种语言描述每一个、
运行记录标明拓扑及其成本，且 `make ci` 全绿时，本特性完成。
