# 概要设计（HLD）：在 Kubernetes Pod 内执行只读命令

> **特性 ID**：`004-kube-exec` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它处在哪个位置

```
知识包 ── inspect 命令 ──► kube.exec 工具
                              │  Plan() → safety.Call{Exec: …}
                              ▼
                        tool.Invoker ──► safety.Guard.Authorize
                              │              ├─ 命令白名单
                              │              └─ exec 路径规则
                              ▼
                        kube.ExecClient ──► GET …/pods/{p}/exec（升级）
                                                 │
                                        v4.channel.k8s.io 帧
                                        ├─ 通道 1 stdout
                                        ├─ 通道 2 stderr
                                        └─ 通道 3 status（退出码）
```

护栏的位置没有任何变化：工具在效果发生**之前**声明它，
invoker 仍是通往工具的唯一路径，护栏仍是唯一的授权者。

## 2. 两条不变量，都可机械检查

既有那条被原样保留：

> **`Client` 无法表达变更。** 每个方法都发 GET，且方法名不得含有
> `Exec`、`Attach`、`PortForward`、`Create`、`Delete`……

因此执行能力落在第二个类型上，而它也赢得一条同类的第二不变量：

> **`ExecClient` 只能访问一个端点。** 它只有一个导出方法、不接受路径参数，
> 其 URL 由 namespace、Pod 与容器拼成。不存在任何输入能让调用方把它指向别处。

两者都靠"名字与形态"而非"读函数体"来检查 —— 正是这一点，
让它们能在一位没读过本文档的维护者手里存活下来。

## 3. 为什么这个效果是"一个"而不是"两个"

一次 exec 既是一个 HTTP 请求，又是一次命令执行。若把它建模成两次 `Authorize`，
就等于把"如何组合这两项检查"交给了调用方；而漏掉命令那一项的调用方，
照样能编译、照样能运行 —— 直到有人去读代码之前，这个失败都是不可见的。

于是护栏新增一个效果：

```
ExecEffect{ Namespace, Pod, Container, Binary, Args }
```

授权它时要求**两项约束同时成立**：

1. `Binary` 与 `Args` 通过与本地适配器完全相同的命令白名单 ——
   同样的规则、同样的变更性动词识别、同样的取值白名单；
2. 该效果所隐含的 URL 匹配 exec 路径规则，且别无其他。

有一个结论值得直说：**本特性没有新增任何命令。**
`redis-cli INFO` 本来就被允许，现在只是多了一个可运行的地方；
`redis-cli FLUSHALL` 本来就被拒绝，现在仍被拒绝，
错误码完全相同，且发生在任何连接建立之前。

## 4. 被污染的提示词能触及什么

真正要紧的威胁不是恶意的运维人员，而是一个读过攻击者可控日志行、
此刻正想执行点什么的模型。可触及集合由四件互相独立的事界定，
放宽其中任何一件都属于规格变更：

| 边界 | 由什么设定 | 提示词能放宽它吗 |
|---|---|---|
| 哪些二进制 | 护栏的命令白名单 | 不能 —— 默认拒绝，且没有配置项能放宽 |
| 哪些参数 | 变更性动词识别与按 flag 的取值白名单 | 不能 |
| 哪些 Pod | 目标解析出的实例集合 | 不能 —— 工具接收的是实例，而不是 Pod 名 |
| 哪个端点 | `ExecClient` 固定的 URL 形态 | 不能 —— 根本没有路径参数 |

`stdin` 与 TTY 的缺席正是出于这个原因，而不是为了省事：
两者都会把"一次性读取"变成会话，而会话是可被操纵的。

## 5. 传输

Kubernetes 的 WebSocket 远程命令是一次带 RFC 6455 升级头、
并携带 `v4.channel.k8s.io` 子协议的 `GET`。
每个二进制帧的第一个字节是通道号，其余是负载。
通道 3 在结束时投递一段 JSON status —— 退出码就来自那里。

由此产生两个塑形设计的结论：

- **护栏中不会引入新的 HTTP 动词。** exec 路径规则是一条 `GET` 规则，
  就排在它两侧的 Pod 规则与日志规则之间。
- **实现小而自足**：一次握手、一个帧读取器、一个三路解复用器。
  它对着一个从服务端侧说真协议的测试服务端受测，
  因此客户端绝不会只对着自己假设的镜像受测。

## 6. 降级

每一种失败都变成带码的缺口，而不是一次失败的运行：

| 失败 | 变成 |
|---|---|
| 命令不在白名单 | 连接之前即拒绝，沿用既有 `MAS-8002`/`MAS-8001` |
| 该环境已关闭 exec | 一条说明该策略的缺口，让读者知道这项检查不是"被顺手跳过" |
| 升级被拒（RBAC、Pod 不存在、apiserver 策略） | 一条点明原因的带码缺口 |
| 非零退出 | 证据**加**缺口：命令跑了并给出了不同意见，这本身就是一个结果 |
| 输出超过上限 | 截断后的证据，外加一条说明截掉了多少的缺口 |
