# 特性规格：Case 语料库与评测框架

> **特性 ID**：`006-eval-harness` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.1.4
> **宪法**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

已经有三个特性以同一句话收尾：*本项目只做拓扑之间的对比，不做打分，
因为打分需要一个带已知根因的 case 语料库。* 这句话每一次都是诚实的，
而如今它正是横在本项目与"当初促成可切换架构的那个目标"之间的东西 ——
用实验而不是口味来定一个设计问题。

现有的是**成本**上的对比：演示把同一个案例跑过五种拓扑，打印模型调用数、工具调用数与金额。
缺的是**结果**上的对比。今天没有任何东西能回答："`debate` 是否比 `supervisor`
更常得出正确结论？在哪一类故障上？"

还有第二种用途，没那么光鲜，却更可能天天用得上。六个知识包如今包含约两百个阈值，
而没有任何东西检查某个知识包是否仍能得出它过去能得出的结论。
语料库就是领域知识的回归测试套件 —— 这是任何单元测试都做不到的。

本特性绝不能踩进去的风险，是造出一个**看起来像准确率、实则不是**的数字。
合成语料库度量的是"与它自己标签的一致程度"；基于文本相似度的打分器奖励的是复述；
而对着 mock provider 跑一遍，度量的是脚本而不是模型。
这三者中的任何一个都会给出一个自信的数字，其含义与读者的默认理解并不相同 ——
而一个误导性的度量比没有度量更糟：它会终结那些本该继续下去的争论。

## 2. 用户与场景

| 角色 | 目标 | 触发 |
|---|---|---|
| 平台工程师 | 用证据而不是口味来选定默认拓扑 | 评估该工具时 |
| 知识包作者 | 确认自己的改动没有破坏原本成立的结论 | 修改阈值时 |
| 维护者 | 捕捉规则引擎中任何单元测试都覆盖不到的回归 | 每一次 CI |
| 研究者 | 在同一批案例上比较模型 × 拓扑 | 研究该设计时 |

## 3. 范围

### 范围内
- 把 **case** 作为带版本的数据：桩遥测、日志、诊断目标、症状，
  以及一次正确诊断应当得出的结果。
- 随项目发布的语料库，取材自各知识包的故障模式。
- 一个把 case 端到端跑过**真实**技术栈（真采集器、真护栏、真引擎）并打分的框架。
- 只依据**可机械检查的事实**打分：得出了哪个故障模式、是否得出了该 case 明确排除的结论、
  是否声明了预期中的缺口。
- 跨拓扑的矩阵运行，以及稳定的结果报告。
- 对"这个数字**不**代表什么"的醒目且无法回避的声明。
- 语料库出现回归时让 CI 失败的闸门。

### 范围外
- 用与参考答案的相似度给自由文本打分。那会奖励复述提示词的模型，
  也会让语料库离开"参考答案撰写者"就无法扩展。
- 把正确性、成本与时延压成一个"质量分"。
  三者之间如何取舍是读者的事；把它藏进一组权重里，等于替读者悄悄做了决定。
- 真实故障数据。录制生产遥测是一个本项目尚未提出的隐私问题。
- 针对语料库调提示词。一个被用来拟合的语料库，就不再是度量了。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | case 必须是数据：新增一个 case 不得需要重新编译 | P0 | `TestCorpusLoadsFromDirectory` |
| FR-002 | case 必须声明一次正确诊断应得出的故障模式，并可声明它绝不应得出的模式 | P0 | `TestCaseSchemaRequiresAnExpectedOutcome` |
| FR-003 | 框架必须让 case 跑过真实的 service、采集器与护栏，而不是它们的模拟 | P0 | `TestHarnessUsesTheRealPipeline` |
| FR-004 | 打分只能使用可机械检查的事实；不得使用文本相似度打分 | P0 | `TestScoringUsesNoTextSimilarity` |
| FR-005 | 错误结论（case 明确排除的模式）必须与"漏判"分开报告 | P0 | `TestFalseConclusionIsScoredSeparately` |
| FR-006 | case 可以刻意扣留某个遥测源，框架必须检查该次运行是否声明了由此产生的缺口 | P0 | `TestWithheldSourceMustProduceADeclaredGap` |
| FR-007 | 框架必须能跑矩阵：每个 case × 所选的每个拓扑 | P0 | `TestMatrixRunsEveryCaseAgainstEveryTopology` |
| FR-008 | 在确定性 provider 下结果必须确定，从而让"回归"意味着真实变化 | P0 | `TestResultsAreDeterministic` |
| FR-009 | 对着 mock provider 的运行必须声明它度量的是脚本而非模型，且不得把 Agent 阶段的结果当作模型质量呈现 | P0 | `TestMockRunRefusesToClaimModelQuality` |
| FR-010 | 输出必须按 case 报告结果与合计，且绝不给出单一的压缩分数 | P0 | `TestReportKeepsOutcomesSeparate` |
| FR-011 | `mas eval` 必须能从 CLI 跑语料库，且支持两种语言 | P1 | CLI 测试 |
| FR-012 | 已发布 case 出现回归时 CI 必须失败 | P1 | `make ci` 会跑语料库 |
| FR-013 | 语料库必须覆盖每一个已发布的知识包 | P1 | `TestEveryPackHasACase` |

## 5. 非功能需求

| ID | 需求 | 度量 |
|---|---|---|
| NFR-001 | 在确定性 provider 下，整个语料库在 CI 中必须 60 秒内跑完 | 计时测试 |
| NFR-002 | 不引入新的模块依赖 | `go.mod` 无变化 |
| NFR-003 | 每一个面向运维人员的字符串都双语 | `sddctl verify` |
| NFR-004 | case 不得放宽护栏，也不得触达真实网络 | 结构审计；仅使用桩服务端 |
| NFR-005 | 凡是展示结果的地方，都必须说明该语料库是合成的 | 两种语言的输出测试 |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 一项度量绝不得被呈现得超出它本身 | 宪法第九条 |
| CON-002 | 不得有单一的压缩分数 | §3 范围外 |
| CON-003 | 语料库是合成的，且每一次都要说明 | NFR-005 |
| CON-004 | case 是数据，遵循与知识包相同的双语规则 | 第三条 |
| CON-005 | 框架不得调优任何东西；它只做度量 | §3 范围外 |

## 7. 验收

当 `mas eval` 能把已发布语料库跨全部拓扑跑过真实流水线、
按 case 报告结果并把错误结论单独计数、明说这些数字不代表什么、
在回归时让 CI 失败，且 `make ci` 全绿时，本特性完成。
