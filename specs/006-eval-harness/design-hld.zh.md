# 概要设计（HLD）：Case 语料库与评测框架

> **特性 ID**：`006-eval-harness` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它处在哪个位置

```
case（YAML）──► 桩 Prometheus + 桩 Loki（真实 HTTP）
                          │
                          ▼
              config ──► service.Diagnose ──► 报告
                          │                     │
              真实采集器、护栏、                 ▼
              规则引擎、拓扑                eval.Score(case, report)
                                                │
                                    Outcome{命中、错误结论、缺口、成本}
                                                │
                                      矩阵 · 渲染 · CI 闸门
```

框架位于系统**之外**，并从运维人员使用的同一扇门驱动它。
它不给产品新增任何接口：`service.Diagnose` 正是 `mas diagnose` 所调用的那个，
它触达的采集器也正是一次真实运行会触达的那些。
一个注入桩工具的框架写起来更快，度量的却是没人在跑的那个系统。

## 2. 一个 case 断言什么

case 是一次故障，加上一次正确诊断应当得出的结果。
它只断言流水线本就提交的东西，且使用知识包定义的词表：

| 字段 | 含义 | 为何可检查 |
|---|---|---|
| `expect.failure_modes` | 正确诊断应得出的模式 | 知识包声明的 id |
| `expect.not_failure_modes` | 绝不应得出的、看似合理的错误答案 | 知识包声明的 id |
| `expect.gaps` | 给定 case 扣留了什么，运行必须声明的缺口 | 错误码 |

不存在参考答案文本，打分也从不读散文。
代价是 case 无法度量"解释得有多好"—— 文档会直说这一点，
而不是让读者默认那个数字已经把它涵盖了。

## 3. 四个数字，绝不合成一个

一个 case 的每次运行产出四项事实，且彼此分开：

| 结果 | 含义 |
|---|---|
| **命中** | 每一个预期模式都被得出 |
| **漏判** | 某个预期模式未被得出 |
| **错误结论** | case 明确排除的模式**被**得出了 |
| **缺口** | 预期缺口是否被声明 |

外加其成本与耗时。

它们从不被合并。漏判与错误结论是两种不同的失败：
前者让运维人员留在原地，后者自信地把他们送错方向。
加权求和会让"用前者换后者"的改动看起来像进步 ——
而这恰恰是基于 LLM 的系统在被推着"更果断"时会做的那个交换。

## 4. 这些数字不代表什么

有三句话会随每一次结果、以运维人员的语言一同渲染 ——
因为写在手册里的限定，在有人截图那张表的那一刻并不在场：

1. **语料库是合成的。** 它度量的是与它自己标签的一致程度，
   而不是在真实故障上的准确率。满分意味着系统的行为符合语料库作者的预期 ——
   这是一个更弱、但有用的主张。
2. **mock provider 的运行度量的是脚本。** 脚本化对话里本就写着答案，
   因此 Agent 阶段的结果对模型不说明任何事情。
   框架只报告确定性阶段，并拒绝把其余部分当作模型质量呈现。
3. **成本的可靠程度不会高于价格。** 未定价的模型会让它变为未知，与别处一致。

## 5. 为什么要用真实流水线

最可能发生回归的部分，恰恰是走捷径会跳过的那些：
信号展开成的 PromQL、护栏对它的裁定、采集器的解析、引擎对空值的处理。
过去三个特性中发现的每一个缺陷，都恰好住在这一层 ——
正则字面量被当成槽位名、空 series 被读成健康、引用指向了不存在的东西。

因此框架用桩服务端提供真实 HTTP，并让 socket 之下游的一切都是生产路径。
它的代价是每个 case 多几百毫秒，换来的是对**真正发布的那个系统**的度量。

## 6. 本设计不做的事

- **针对语料库调提示词。** 被用来拟合的语料库就不再是度量；
  一旦被那样使用，它的数字就不再是那些限定所说的含义了。
- **真实故障数据。** 录制生产遥测是一个本项目尚未提出的隐私问题，
  而通过发布一个录制器来悄悄回答它，是提问方式里最糟的一种。
- **排行榜。** 比较拓扑才是要点；
  在十来个 case 的合成语料库上给它们排一个永久名次，是一句披着表格外衣的无依据断言。
