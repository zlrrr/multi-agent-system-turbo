> **双语对应文件**：[`plan.md`](./plan.md) · **上游**：[`spec.zh.md`](./spec.zh.md) v1.0.0 · **下游**：[`design-hld.zh.md`](./design-hld.zh.md)

## 1. 技术上下文

| 方面 | 决策 |
|---|---|
| 语言 / 运行时 | 无新增：本特性只新增 YAML 数据与一个测试文件 |
| 新增依赖 | 无 |
| 工作落点 | `internal/knowledge/packs/*.yaml`、`internal/knowledge/conformance_test.go`、`docs/{en,zh}/knowledge-packs.md` |
| 测试策略 | 一个覆盖全部内置包的表驱动一致性测试，外加守卫校验与表达式编译检查 |

真正有意思的约束是本特性**不允许**做什么。`spec.zh.md` 的 CON-004 禁止修改加载器。如果某个包
无法用当前 Schema 表达，那是一条关于 Schema 的发现，值得记录，而不是在特性中途放宽 Schema 的
许可证 —— “新增中间件只需一个数据文件”这个论断此刻正在被检验，而这是它第一次接受真实考验。

## 3. 阶段分解

| 阶段 | 产出 | 退出条件 |
|---|---|---|
| A | 一致性测试，先针对已有两个包编写 | 对 Redis 与 Kafka 通过，并对刻意做浅的包给出有信息量的失败 |
| B | MongoDB 知识包 | 一致性通过；剧本对桩遥测产出结论 |
| C | Pulsar 知识包 | 同上 |
| D | Milvus 知识包 | 同上 |
| E | OceanBase 知识包 | 同上 |
| F | 双语编写指南 | `sddctl verify` 对等性通过 |

先写测试在这里不是走形式。一个在四个包之后才写的一致性测试，其形状必然被这四个包碰巧包含的
内容所塑造 —— 而这恰恰是本特性想要避免的失败模式。

## 5. 风险

| ID | 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|---|
| RSK-001 | 知识看似合理但实际错误，而运维人员照做了 | 中 | **高** | 每个信号都是真实 exporter 指标名并记录在编写指南中；每个失效模式解释机制而非复述症状；每条可能丢数据的建议都标为高风险 |
| RSK-002 | 指标名在 exporter 版本之间漂移 | 高 | 中 | 剧本把缺失信号当作缺口而非错误读数 —— 既有引擎已经这样做。编写指南说明如何重新映射 |
| RSK-003 | 某个包需要 Schema 尚不支持的能力 | 低 | 中 | 记录为一条发现，并在不带该规则的情况下发布该包，而不是在特性中途放宽 Schema |
| RSK-004 | 快速写出的四个包比慢慢写的两个包更浅 | 中 | 中 | 一致性测试为全部六个包设定同一条下限 |

## 6. 复杂度追踪
