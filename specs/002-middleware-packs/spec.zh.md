# 特性规格说明：中间件知识广度

> **特性 ID**：`002-middleware-packs` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.1.0
> **宪章**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

MAS-Turbo 目前内置了 Redis 与 Kafka 的专家知识。项目目标中另外点名了四种中间件 ——
MongoDB、Pulsar、Milvus、OceanBase —— 而今天运行其中任何一种的运维人员，拿到的诊断都没有
领域支撑：只有通用证据，没有失效模式，没有经过审核的建议，也没有确定性剧本。于是每一次常规
故障都会落到模型调用上，而模型只能对一个从未被告知任何信息的系统做第一性原理推理。

架构本身早已为此留好了位置：知识是带版本的数据，且 `TestPackOnlyMiddlewareAddition` 已经证明
仅凭一个文件就能新增一种中间件。缺的是知识本身，以及第三方编写自己知识包所需的指导。

因此本特性是*数据与文档*，而不是架构。它的风险不在于代码跑不通 —— 而在于知识可能浅薄、
似是而非且错误。那比没有知识更糟，因为运维人员会照着它去行动。

## 2. 用户与场景

| 角色 | 目标 | 触发条件 |
|---|---|---|
| 运行 MongoDB 的 SRE | 以与 Redis 同等的深度诊断副本集或写关注问题 | MongoDB 目标触发告警 |
| 运行 Pulsar 的 SRE | 诊断积压、ledger 或 bookie 问题 | 消费积压持续增长 |
| 运行 Milvus 的 SRE | 诊断查询节点时延或卡住的 compaction | 向量检索时延上升 |
| 运行 OceanBase 的 SRE | 诊断租户资源耗尽或合并缓慢 | 租户反馈写入卡顿 |
| 平台工程师 | 为我们未内置的中间件编写知识包 | 希望沉淀自己的专业经验 |

## 3. 范围

### 范围内
- MongoDB、Pulsar、Milvus、OceanBase 的知识包，各自包含信号、日志模式、带审核建议的失效模式、
  确定性剧本与只读巡检命令。
- 一致性测试，所有内置知识包都必须满足 —— 这会抬高全部六个包的下限，而不只是新增的四个。
- 双语知识包编写指南，附公开 Schema。
- 新增巡检命令所需的守卫白名单条目（若有）。

### 范围外
- 超出这四个包真实需要之外的 Schema 变更。
- Kubernetes 容器内 `exec`（M2，独立特性）。
- 新增拓扑（M2，独立特性）。
- 包内按版本区分的规则变体（M3）。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 系统 MUST 内置 MongoDB 知识包，至少覆盖复制、写关注、连接饱和、慢操作、锁竞争与存储压力 | P0 | 一致性测试逐项点名失效模式 |
| FR-002 | 系统 MUST 内置 Pulsar 知识包，至少覆盖积压增长、bookie 与 ledger 健康、broker 负载与订阅问题 | P0 | 一致性测试逐项点名失效模式 |
| FR-003 | 系统 MUST 内置 Milvus 知识包，至少覆盖查询节点时延、compaction、索引构建与内存压力 | P0 | 一致性测试逐项点名失效模式 |
| FR-004 | 系统 MUST 内置 OceanBase 知识包，至少覆盖租户资源上限、合并/compaction 与慢 SQL | P0 | 一致性测试逐项点名失效模式 |
| FR-005 | 每个内置包 MUST 满足同一个一致性测试：信号、失效模式与剧本的最低数量；双语完整性；每个剧本步骤可达；每个被引用的失效模式均已声明 | P0 | 一个覆盖全部六个包的表驱动测试 |
| FR-006 | 每个包的 `inspect` 命令 MUST 能被安全守卫接受，且任何包都不得声明会被守卫拒绝的命令 | P0 | 测试把全部内置巡检命令送过守卫 |
| FR-007 | 每个失效模式 MUST 至少携带一条建议，且任何内置建议都不得表述为“已执行的动作” | P0 | 一致性测试断言其存在，并扫描过去完成时表述 |
| FR-008 | 系统 MUST 发布双语知识包编写指南，说明 Schema、表达式环境与一致性规则 | P0 | `docs/{en,zh}/knowledge-packs.md` 存在且对等性检查通过 |
| FR-009 | 每条剧本表达式 MUST 在发布前能在沙箱环境中编译通过 | P0 | 测试编译全部内置包中的每条表达式 |
| FR-010 | 新增这些包 MUST NOT 需要对 `internal/knowledge` 做任何超出既有 Schema 校验范围的改动 | P0 | diff 不触及加载器逻辑 |

## 5. 非功能需求

| ID | 类别 | 需求 | 度量方式 |
|---|---|---|---|
| NFR-001 | 正确性 | 使用的每个指标名 MUST 来自真实、广泛部署的 exporter，不得杜撰 | 每个信号的来源 exporter 记录在编写指南中 |
| NFR-002 | 诚实性 | 知识包 MUST NOT 声称一个它没有任何信号或日志模式可检测的失效模式 | 一致性测试交叉核对 indicators 与已声明信号 |
| NFR-003 | 体积 | 内置知识包 MUST NOT 使二进制超过 15 MB | 构建体积闸门 |
| NFR-004 | 确定性 | 给定症状的剧本选择 MUST 保持稳定 | 既有确定性测试继续通过 |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 所有面向运维人员的字符串双语完整 | 宪章第三条 |
| CON-002 | 巡检命令在调用时由守卫重新校验 | 宪章 IV.2 |
| CON-003 | 建议仅为建议；任何建议都不得读起来像已执行的动作 | 宪章 IV.3 |
| CON-004 | 不改加载器：Schema 必须已经支持这些包 | 001-mvp-core FR-007 |

## 7. 假设

| ID | 假设 | 若假设不成立 |
|---|---|---|
| ASM-001 | 运维人员使用主流 exporter：`percona/mongodb_exporter`、Pulsar 内置 Prometheus 端点、Milvus 内置指标、OceanBase 的 `obagent` | 包中信号会落空；编写指南说明如何重新映射 |
| ASM-002 | 在各项目支持的版本范围内，指标名足够稳定 | 按版本区分的规则（M3）会更早成为必需 |

## 8. 待决问题

| ID | 问题 | 是否阻塞？ | 采用的默认值 |
|---|---|---|---|
| OQ-001 | 每个包在发布前应做到多深？ | 否 | 与 Redis 包保持同一形态：≥10 个信号、≥6 个失效模式、≥3 个剧本。再深入属于迭代范畴 |
| OQ-002 | 知识包是否应声明 exporter 版本区间？ | 否 | 暂不；`versionRange` 针对的是中间件本身，exporter 漂移问题在编写指南中说明 |
