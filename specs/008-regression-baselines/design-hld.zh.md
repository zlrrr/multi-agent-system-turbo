# 概要设计（HLD）：回归基线与模型维度

> **特性 ID**：`008-regression-baselines` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`design-hld.md`](./design-hld.md) · **上游**：[`plan.zh.md`](./plan.zh.md) v1.0.0 · **下游**：[`design-lld.zh.md`](./design-lld.zh.md)

## 1. 它位于何处

```
  语料库 ──► Runner.Matrix ──► []Outcome ──┬──► Summary.Regression()   绝对闸门
             (case × 拓扑                    │                          （特性 006）
              × 模型，新增)                  │
                                             └──► Compare(baseline) ──► Delta
                                                        ▲                 │
                                          baseline.json │                 ├─ 回归      → 失败
                                                        │                 ├─ 改善      → 展示
                                                   --write-baseline       ├─ 已知为坏  → 展示
                                                   （由人写入，           ├─ 新增      → 展示
                                                     绝不由运行写入）      └─ 未运行    → 展示
```

`[]Outcome` 之上的一切都没有变化，只有一个循环多了一维。
所有新增内容都只是对已有结果做算术 —— 这既是 NFR-001，
也是这个特性之所以很小的原因：当特性 006 决定"不把一个结果压缩成一个数字"时，
它就已经把难的那部分做完了。

## 2. 基线是什么，以及它拒绝成为什么

诱人的那种基线是一块记分牌：按拓扑记下命中数与漏判数，按总数比较。
它会在任何人遇到的第一个例子上失效。一次把一个命中变成错误结论、
又把一个漏判变成命中的改动，会让所有总数都保持不变 ——
而这两次移动，恰恰是特性 006 拒绝去平均的那一对：
一个让运维人员留在原地，另一个自信地把他们送错方向。

因此，基线记录的是**格子**，而不是计数。一个格子是一组（case、拓扑、模型），
被记录下来的是它的结果类别，以及使它成为该类别的那些 id：

```
kafka-broker-loss-under-replicated / supervisor / mock-1
  → miss, missing=[broker-loss]
```

于是比较就是逐格的状态转移，而每一种转移都有名字：

| 原来 | 现在 | 名称 | 闸门 |
|---|---|---|---|
| hit | hit | —— | 通过 |
| hit | 其他任何 | **回归** | **失败** |
| 非 hit | hit | **改善** | 通过，并展示 |
| 非 hit | 非 hit，id 相同 | **已知为坏** | 通过，且每次运行都列出 |
| 非 hit | 非 hit，id 不同 | **失败方式改变** | 通过，并展示 |
| 不存在 | 任何 | **新增** | 通过，并展示 |
| 任何 | 不存在 | **未运行** | 通过，并展示 |

没有任何东西被相加，因此没有任何东西能相互抵消。
一次修好两个格子、弄坏一个格子的改动，会产出两条"改善"与一条"回归"，
由评审的人来做决定 —— 这正是"什么变了？"这个问题真正想要的。

## 3. "已知为坏"是一等状态

最重要的是第四行。一旦某个格子确实无法通过 —— 一个没人有时间去补的知识缺口 ——
绝对闸门就只留下一条让 CI 变绿的路：删掉这个 case。
这是最坏的激励，因为这个 case 是"该缺口存在"的唯一记录。

把这次失败记进基线，可以同时让闸门保持绿色**并且**让缺口保持可见。
比较结果会在每一次运行中列出每一个已知为坏的格子，而不只在它变化时才列，
从而让它一直摆在有能力去补它的人面前（RSK-2）。
而一个开始以**不同方式**失败的已知为坏格子会被报告，
因为"它为何失败"本身就是被记录下来的一部分 ——
一个原先漏掉某个故障模式、如今却得出了一个错误结论的格子，确实动了，
尽管两种情况都属于"不是 hit"。

## 4. 模型维度

`Runner.Matrix` 已经在做 case × 拓扑的叉乘。再叉乘上模型，
只是同一个循环多一维，没有任何新概念 —— 但有一件事必须做对：
格子必须携带产出它的那个模型。

否则，逐格记账就会把成本归到"最后一次恰好被配置"的那个模型头上，
而这比根本不报告成本更糟：它看上去很权威，实际上是错的。
因此模型会随结果从运行它的那个作业一路带过来，
并由一个测试断言"逐格记账"而不是"整次运行的记账"。

跨模型的比较，是本特性明知会被运维人员过度解读的唯一一处。
在确定性 provider 下，一个格子是一次测量；在真实模型下，它是**一次抽样**，
而同一个模型的两次抽样可以不同。本项目不打印自己支撑不了的置信区间，
所以答案是披露而不是统计：每一次比较都会声明每格只是一个样本，
且这句声明会以字段形式随 JSON 一同传递，使格式化程序无法把它丢掉。

## 5. 刻意不做的事

- **不自动更新基线。** 会自我更新的基线记录的是"发生了什么"，因此永远不会失败 ——
  那是一次毫无意义的绿色构建。写入是人的行为，并落在一份可评审的 diff 里。
- **不做显著性检验。** 本工具跑的就是每格一个样本。
  由此算出的置信区间，正属于那种"读起来像严谨、实则毫无严谨"的数字。
- **不为真实 provider 发布基线。** 一个每次运行都会变的文件不是基线。
  仓库自身的基线在确定性 provider 下记录，覆盖的就是内置语料库。
- **不做调优。** 本装置只做测量。特性 006 拒绝让它优化任何东西，
  而基线让这条拒绝更重要而不是更不重要：基线恰恰就是你会去拟合的那个东西。
