# 特性规格：回归基线与模型维度

> **特性 ID**：`008-regression-baselines` · **版本**：1.0.0 · **状态**：已批准
> **双语对应文件**：[`spec.md`](./spec.md) · **上游**：[`docs/zh/project-goals.md`](../../docs/zh/project-goals.md) v1.1.7
> **宪法**：`.specify/memory/constitution.zh.md` v1.0.0 · **下游**：`plan.zh.md`

## 1. 问题陈述

特性 006 为本项目带来了语料库与闸门。这个闸门是绝对的：
只要有任何 case 漏判或得出被排除的结论，`mas eval` 就失败。
对一个当前全部通过的语料库来说，这是正确的标准，
但它只回答了一个问题 ——"是不是还全绿？"

它回答不了任何人在改动之后真正会问的那个问题：**什么变了？**
一次修好两个 case、又弄坏一个 case 的知识包改动，呈现出来只是"语料库出现回归"，
没有任何办法看清这笔交易。一次在 `debate` 下丢掉一个命中、
又在 `single` 下多出一个命中的提示词改动，呈现出来就是红色，
而做出这次改动的人只能把矩阵跑两遍，再用肉眼去 diff 两个终端。
最糟的是：一旦某个 case 确实无法通过 —— 一个没人有时间去补的知识缺口 ——
让 CI 保持绿色的唯一办法就是删掉这个 case，而这恰恰是最坏的激励。

第二半是模型维度。G7.3 要求在**模型 × 拓扑**矩阵上做回归打分，
而今天只有拓扑这一维：`--matrix` 变化的是拓扑，模型是固定的。
一位要在便宜模型与强模型之间做选择的运维人员，只能自己写脚本去跑这个扫描，
并因此失去共享的记账 —— 每个格子的成本、每个格子的调用次数 ——
而正是这些记账让这种比较变得有意义。

## 2. 用户与场景

| 角色 | 目标 | 触发时机 |
|---|---|---|
| 知识包作者 | 分别看清一次知识改动修好了什么、又弄坏了什么 | 任何一次知识包改动 |
| 维护者 | 让 CI 因"变差的格子"而失败，而不是因"早就已知为坏的格子"而失败 | 每一次构建 |
| 平台工程师 | 在同一批 case 上比较两个模型，并把成本摆在结果旁边 | 选择默认模型 |
| 研究者 | 拥有一份可记录、可 diff 的系统表现产物 | 汇报结果时 |

## 3. 范围

### 范围内
- **基线**：按（case、拓扑、模型）格子记录的结果。
- 将一次运行与基线做比较，**分别**报告回归与改善。
- 一个相对基线判定回归的闸门，使已知为坏的格子保持可见，而不是被删掉。
- 写入与更新基线，作为一次显式、可评审的行为。
- **模型维度**：`--models` 让每个指定模型跑遍同一批 case 与拓扑，并带每格记账。
- 在展示比较结果的任何地方，都说明"每格一个样本"能支撑什么、不能支撑什么。

### 范围外
- 统计显著性。本工具跑的就是每格一个样本；由此声称一个置信区间，
  正属于本项目拒绝打印的那类数字。
- 自动更新基线。会自我更新的基线，记录的是"发生了什么"，因此永远不会失败。
- 为非确定性 provider 发布基线。仓库中的基线在确定性 provider 下记录，
  因为一个每次运行都会变的文件不是基线。
- 针对基线做任何调优。本装置只做测量，不做优化（特性 006，CON-005）。

## 4. 功能需求

| ID | 需求 | 优先级 | 验收信号 |
|---|---|---|---|
| FR-001 | 基线必须为每个（case、拓扑、模型）格子记录一条结果，并记录其记录时所用的 provider | P0 | `TestBaselineRecordsEveryCell` |
| FR-002 | 只有被显式要求时才能写入基线 | P0 | `TestBaselineIsNeverWrittenImplicitly` |
| FR-003 | 比较必须分别报告回归与改善，绝不相互抵消 | P0 | `TestRegressionsAndImprovementsAreReportedSeparately` |
| FR-004 | 原本就失败、且以同样方式继续失败的格子，不得让闸门失败 | P0 | `TestKnownBadCellDoesNotFailTheGate` |
| FR-005 | 原本失败、现在以**不同方式**失败的格子必须被报告 | P1 | `TestChangedFailureIsReported` |
| FR-006 | 出现在本次运行但不在基线中的格子，必须报告为新增，而不是回归 | P0 | `TestNewCellIsNotARegression` |
| FR-007 | 出现在基线但本次未运行的格子，必须报告为未运行 | P0 | `TestMissingCellIsReported` |
| FR-008 | 与在不同 provider 或模型下记录的基线做比较时，必须在展示结果的任何地方说明这一点 | P0 | `TestProviderMismatchIsDisclosed` |
| FR-009 | `--models` 必须让每个指定模型跑遍每个 case 与每个拓扑 | P0 | `TestModelAxisRunsEveryCell` |
| FR-010 | 每格的记账 —— 调用次数、token、成本 —— 必须归属到花掉它的那个模型 | P0 | `TestPerCellAccountingIsAttributed` |
| FR-011 | 比较结果必须说明"每格一个样本"能支撑什么 | P0 | `TestComparisonCarriesTheSamplingCaveat` |
| FR-012 | 基线文件在多次运行间必须逐字节稳定，使 diff 只显示真实变化 | P0 | `TestBaselineIsByteStableAcrossRuns` |
| FR-013 | CLI 上的 `mas eval --baseline`、`--write-baseline`、`--models`，两种语言 | P1 | `TestEvalBaselineCLI` |
| FR-014 | 仓库必须为自己的语料库发布一份基线，且 CI 必须与之比较 | P1 | `TestShippedBaselineMatchesTheCorpus` |

## 5. 非功能需求

| ID | 需求 | 度量 |
|---|---|---|
| NFR-001 | 比较不增加任何运行时间：它只是对已产出结果做算术 | 计时测试 |
| NFR-002 | 不引入新的模块依赖 | `go.mod` 未变 |
| NFR-003 | 每一条面向运维人员的字符串都是双语 | `sddctl verify` |
| NFR-004 | 发布的基线仍留在特性 006 设定的 CI 预算之内 | `TestCorpusRunsInsideTheCIBudget` |

## 6. 约束

| ID | 约束 | 来源 |
|---|---|---|
| CON-001 | 无论基线还是比较结果，都不给出压缩分数 | 特性 006 CON-002 |
| CON-002 | 一次测量绝不被呈现为超出其本身的东西 | 宪法第九条 |
| CON-003 | 基线由人写入，绝不由一次运行写入 | §3、FR-002 |
| CON-004 | 每条消息都要有两种语言 | 第三条 |

## 7. 验收

当满足以下条件时，本特性完成：一次运行可以与已记录的基线做比较；
回归与改善并排报告且绝不相互抵消；已知为坏的格子在保持可见的同时不会让 CI 变红；
模型维度可以运行并带每格成本；每一次比较都说明"一个样本"能支撑什么；
且仓库自身的基线已提交并由 CI 强制执行。
